# 0030 — 성능 넘김 흔들림은 실패 회차의 원문으로 가르고, 근거가 선 쪽을 한 PR 에서 고친다

2026-10-15 · 결정함 · 셋 다 저자가 착공 대화에서 정했다 — 세션이 지난 측정 · 「고정한 것」 · 조각 18 · 19 에서 끌어내 추천한 쪽이다

## 맥락

`gap-unowned` 의 `gate-escalated-perf` 가 전수 세 번 연달아 떨어졌다 — 2026-10-07 첫째 한 회차 · 둘째 두 회차, 2026-10-13 한 회차. 문턱(0.8)을
넘어 세 번 다 「한 회차씩 흔들린 것」으로만 적혔고, 어느 기록도 실패 회차의 원문을 보지 못했다(`docs/eval-log/2026-10.md`). 아티팩트
`eval-result` 셋은 GitHub 에 2027-01 까지 남고, 실패 회차 넷의 트레이스를 든다. 다만 세션 환경이 내려받는 호스트를 허용해야 받는다.

떨어지는 길은 둘이다. 감사자가 성능 발견을 「범위 밖」으로 끝냈을 수 있다 — 2026-10-05 · 06 의 실패는 다 그 모양이었고, 그 뒤 `audit-secrets`
「보지 않는 것」의 성능 줄을 고쳤어도 2/6 · 2/3 이 남았다. 또는 정규식이 바른 기록의 모양을 못 읽었을 수 있다 — 2026-09-22 의 전수 회귀에서
형제 `gate-escalated` 가 그랬고, 「고정한 것」은 이 그레이더를 「번호 목록의 형제 항목을 한 항목으로 읽는다」 한계에 든다.

정규식 그레이더는 고정했다. 고치는 것은 「실제 수트 실행의 트레이스에서 틀린 판정이 나온 경우」뿐이고, 그 모양을 표본으로 박는다
(`vibe-audit/evals/README.md` 「고정한 것」). 감사자 문구는 조각 18 · 19 에서 옛 · 새를 가르지 못한 일이 두 번 있었다. 그 두 번은 수트 모델이
옛 문구로도 바르게 판정했지만, 이 자리는 옛 문구로 실제로 떨어진 회차가 있다.

## 대안

1. 가르는 법: **원문 먼저 — 실패 회차 넷의 트레이스를 그레이더에 대고 감사자 출력과 최종 응답을 대조한다. 원문을 못 받거나 원문이 가르지 못하면
   같은 판을 로컬에서 `--runs 6` 으로 다시 재 실패 트레이스를 얻는다(둘까지)** / 로컬 재측정만 / 원문만.
2. 고칠 쪽: **트레이스가 근거이면 둘 다 — 그레이더는 「고치는 것」 안에서 표본을 박고 고치고, 감사자는 옛 · 새를 같은 픽스처로 가른 뒤에만 문구를
   넣는다** / 그레이더만 고치고 감사자 결함은 조각 나눔으로 넘긴다 / 이 조각은 진단만 하고 고침은 다음 조각으로.
3. PR 나눔: **착공 하나 · 구현 하나(진단과 고침을 한 PR 에)** / 착공 · 진단(eval-log 만) · 고침 셋.

## 결정

굵은 쪽 셋. 저자가 착공 대화에서 정했다(2026-10-15). 셋 다 세션이 추천한 쪽이다.

- 1 은 이미 떨어진 회차가 무엇을 썼는지가 가장 싼 근거이기 때문이다. 원문은 모델을 다시 부르지 않고 갈래를 세우고, 다시 재서는 같은 모양이 나온다는
  보장이 없다 — 떨어지는 빈도가 두 번에 한 번 안팎이다. 다만 프록시가 막을 수 있어 원문에만 기대면 조각이 멈춘다. 재측정만 하면 지난 넷의 모양을
  버리고 새 표본에 기댄다. 재측정을 둘로 묶는 것은 비용(조각 $10)과 같은 측정이 이어지는 것을 막기 위해서다. 둘 다 이 그레이더에서 떨어지지
  않으면 「재현 못 함」으로 둔다.
- 2 는 갈래마다 고칠 자리가 달라서다. 그레이더의 결함이면 「고정한 것」이 허락하는 바로 그 경우다 — 실제 트레이스의 틀린 판정을 표본으로 박는다.
  그것을 넘기면 수트가 바른 기록을 계속 떨어뜨린다. 감사자의 결함이면 관문의 세 번째 자리가 새는 것이라 이 플러그인의 주장에 닿는다. 그러나
  문구는 옛 · 새가 갈려야만 넣는다 — 조각 18 · 19 의 규칙(ADR 0028 · 0029 의 2)과 같은 자다. 진단만 하면 고칠 쪽이 정해진 뒤에도 조각을 하나 더
  열어야 하고, 아티팩트가 남는 동안의 원문을 다시 받아야 한다.
- 3 은 고칠 쪽이 진단으로 정해지고, 고친 머리의 전수가 한 번이기 때문이다. 진단만 따로 머지하면 저자가 결과를 먼저 보지만, 그 몫은 B 안의 eval-log
  첫 커밋과 PR 본문이 든다. 갈래가 섞여도 그레이더 · 감사자 고침은 한 PR 이다 — 그레이더를 먼저 고치고 감사자의 옛 · 새를 그 그레이더로 잰다.

## 결과

- 1: 구현 PR 의 첫 커밋은 eval-log 의 진단이다 — 실패 회차마다 갈래(그레이더 · 감사자 · 받아 적기 · 픽스처 · 러너)와 근거. 트레이스는 저장소에 싣지
  않는다.
- 2: 그레이더로 가르면 `gate-escalated-perf` 와 `samples/pass.md` 가 바뀌고 full 수트 지문이 바뀐다(route 지문 밖이다). 감사자로 가르고 옛 · 새가 갈리면
  `audit-secrets` 「보지 않는 것」 첫 문단이 바뀌고 판이 0.4.1 이 된다. 여섯이 같은 글자로 든 「담당이 없으면」 절은 그대로다. 받아 적기 · 픽스처
  · 재현 못 함 · 못 가름은 고치지 않고 조각을 닫는 기록에서 조각 나눔의 줄로 넘긴다.
- 3: 무엇을 고쳤든 B 의 머리에서 전수를 한 번 돌린다. 고칠 것이 없으면 B 는 eval-log 만이고 전수를 돌리지 않는다.
