# 0034 — 0.4.1 다시 심기는 ADR 0027 대로 `ddcd21f` 에서 하고, `--merge` 줄은 이 조각을 닫는 기록에서 더한다

2026-10-16 · 결정함 · 넷 다 저자가 정했다 — 1 은 착공 대화에서, 2 ~ 4 는 착공 PR(#87)을 연 뒤의 인터뷰에서. 넷 다 세션이 병합 모의 ·
조각 17 · ADR 0027 에서 끌어내 추천한 쪽이다

## 맥락

조각 22 가 「사본을 0.4.1 로 다시 심기」를 넘겼다 — `audit-secrets` 「보지 않는 것」 첫 문단의 끝 문장이 바뀌었고(`5d7f22e`, 판 0.4.1), 두
사본 레포는 0.4.0(`018842c`)이다. 심는 법 · 충돌을 푸는 규칙 · 출처 커밋의 규칙은 ADR 0027 이 정했고, 그 「결과」의 끝 줄이 「다음 심기에서
손 병합을 다시 겪으면 조각 나눔에 `--merge` 줄을 더한다」다. 이 조각이 그 다음 심기다.

2026-10-16 의 병합 모의(조각 23 요구사항 「문제」)에서 ERP 는 여덟 파일 충돌 0 · 바뀐 줄 아홉(머리줄 일곱 · `audit-secrets` 한 줄 · README
의 출처 SHA)이고, 비교기의 판정된 해시 스물일곱이 그대로 남는다. 조각 17 에서는 충돌이 여덟이었고 저자가 ERP PR 에서 풀었다. ADR 0027 의
1 이 `--merge` 를 미룬 까닭은 「특화가 있는 사본 레포는 하나이고 손 병합을 겪어 본 적이 없다」였다.

## 대안

1. `--merge` 줄: **이 조각을 닫는 기록에서 더한다 — C 의 병합 결과(파일마다 충돌 수 · 바뀐 줄 수)와 조각 17 C 의 충돌 여덟을 근거로** /
   착공 PR 에서 더한다(모의만이 근거) / 더하지 않는다 — 충돌 0 이라 ADR 0027 이 미룬 비용(충돌 풀이)을 겪지 않았다 / 이 조각에서
   `sync-agents.sh --merge` 를 세운다.
2. PR 나눔: **넷 — 착공 · 강호쟁패 · ERP · 대장(조각 17 과 같다)** / 대장을 닫는 기록과 한 PR 에.
3. 출처 커밋: **`ddcd21f` — 조각 22 의 구현 PR #85 의 머지, 마스터플랜의 이 줄이 든 커밋** / 심는 날의 `main` 머리(`e90400f`) / 문장을
   바꾼 커밋 `5d7f22e`. 셋 다 `vibe-audit/` 와 `scripts/sync-agents.sh` 의 내용이 같고, 머리줄과 대장에 박히는 SHA 만 다르다.
4. ERP 병합에서 모의와 달리 충돌이 나면: **ADR 0027 의 2 로 풀고 충돌마다 원본 · 사본 · 푼 모양 · 빠지는 것을 ERP PR 본문에 적어 저자가 그
   PR 에서 정한다** / PR 을 열기 전에 멈추고 대화에서 먼저 정한다.

## 결정

굵은 쪽 넷.

- 1 은 줄의 근거가 실제 병합이어야 하기 때문이다. 모의는 `git merge-file` 의 결과를 보였을 뿐이고, ERP 가 조각 중에 사본을 고치면 C 의 결과가
  모의와 다르다. 그 결과가 무엇이든 손 병합을 두 번 겪은 것은 같다 — 조각 17 은 사람이 풀 충돌이 여덟, 이 조각은 모의대로면 사람이 풀 자리가
  없이 같은 명령을 되풀이한 것이다. 뒤의 것이 `--merge` 가 할 일의 모양이다 — 충돌이 없으면 쓰고, 있으면 멈춘다. 더하지 않으면 ADR 0027 의
  「다시 겪으면」을 충돌의 수로 다시 읽는 셈이고, 이 조각에서 세우면 스크립트 고침 · 시험 · 변조본(`CLAUDE.md` 「작업 방식」)이 배포의 남은
  몫에 붙어 조각이 커진다. 줄에는 순서를 매기지 않는다 — 다음 심기 전에 꺼낼지는 그때 정한다.
- 2 는 대장 PR 이 두 사본 PR 의 머지를 기다리고(조각 17 제약 「순서」), 닫는 기록은 대장의 결과(비교기 · `verify-copies.py`)를 대어 보기
  때문이다. 둘을 합치면 닫는 기록이 대어 볼 대장이 아직 머지되지 않은 모양이다. 조각 17 이 같은 나눔으로 하루에 닫혔다.
- 3 은 ADR 0027 의 3 — 대장의 한 줄은 「이 커밋의 원본」을 뜻하고, 두 레포가 같은 커밋을 든다 — 을 따르면서, 0.4.1 을 연 자리를 드는 커밋이기
  때문이다. 조각 22 의 닫는 기록 「배포」와 마스터플랜의 이 줄이 `ddcd21f` 를 가리킨다. `e90400f` 는 ADR 0027 의 3 이 버린 「심는 날의 머리」이고,
  `5d7f22e` 는 #85 가지 안의 커밋이라 머지 커밋으로 읽는 `main` 의 첫 부모 줄에 없다.
- 4 는 조각 17 과 같은 길이기 때문이다 — 충돌을 푸는 것은 사본의 일이라 그 레포의 PR 에서 정하고(`INTENT.md` Not 4), 푼 안이 PR 본문에 서야
  재현(조각 23 설계 ② M6)이 그 안을 든다. 모의가 충돌 0 이라 이 길은 ERP 가 조각 중에 사본을 고칠 때만 쓰인다.

## 결과

- 1: 닫는 기록의 「넘긴 것」에 `sync-agents.sh --merge` 의 순서 없는 줄이 선다(조각 23 성공 기준 8). ERP PR 본문의 파일별 표(조각 23 설계 ②
  M6)가 그 줄의 근거다. ADR 0027 의 1 은 이 조각에서도 그대로다 — ERP 는 손으로 병합한다.
- 2: claude-kit PR 은 셋(착공 · 대장 · 닫기)이고 다 수트 지문 밖이다 — eval 이 돌지 않는다.
- 3: 두 레포 다 `ddcd21f` 의 작업트리(`git worktree add <자리> ddcd21f`)에서 심는다 — 머리줄은 `pdw96/claude-kit@ddcd21f`, 대장 두 줄은 그
  전체 SHA 다.
- 4: 충돌이 나면 ERP PR 이 조각 17 의 #111 처럼 충돌마다 표를 든다. 충돌이 없으면 그 표는 「충돌 0」 한 줄이고 파일별 표(설계 ② M6)만 남는다.
