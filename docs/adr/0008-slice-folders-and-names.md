# 0008 — 조각은 조각 폴더에, 프로젝트 기준은 마스터플랜, 문서의 모양은 절차 지도에

2026-10-06 · 결정함 · 조각 문서의 이름 `plan.md` 는 ADR 0009 가 `requirements.md` 로 바꿨다

## 맥락

조각 2 착공 PR 을 쓰다 보니 `PRD.md` 가 조각마다 절을 쌓아 끝없이 커지고(조각 둘에 207줄), 「PRD」라는 이름이
레포마다 다른 것을 가리켰다 — 강호쟁패는 프로젝트 전체, claude-kit 은 조각 기록. 「기준 문서(baseline)」는 형상
관리의 기준선과, 문서의 모양을 둔 `docs/schema.md` 는 다른 레포의 「데이터 모델」과 이름이 부딪혔다. 그리고 저자가
이 절차를 ERP 에도 적용하기로 했는데, ERP 는 설계도(저장소 밖) → 단계(`PRD.md`, 닫으면 `docs/PRD-N단계.md`) →
조각(자기 설계 게이트, 「짓는 조각이 정한다」 — ERP #98)로 이미 돌고 있다.

## 대안

1. ERP 적용: **(나) 설계대로, ERP 는 다음 단계를 착공할 때부터** / (가) ERP 의 지금 모양에 맞춘다 —
   `PRD.md` 는 지금 조각만, 닫으면 옮긴다.
2. 조각 문서: **`docs/slices/<순서>-<이름>/plan.md · design.md`, `PRD.md` 는 없앤다** / 한글 파일명 /
   `PRD.md` 절 + `docs/design/` 유지.
3. 프로젝트 기준의 이름: **마스터플랜(`docs/master-plan.md`)** / 총괄 문서(`overview.md`) / 기준 문서(`baseline.md`) 유지.
4. 문서의 모양: **절차 지도(`docs/procedure.md`)** / `docs/schema.md` 를 「데이터와 계약의 모양」으로 넓힌다.
5. 설계 ④: **정한 것 / 열어 둔 것(⑥ 의 어느 PR 이 정하나)** / 착공 때 다 정한다.

## 결정

굵은 쪽 다섯 — 저자가 인터뷰에서 하나씩 정했다.

## 결과

- 조각을 닫아도 파일을 옮기지 않는다. 기획과 설계가 한 PR 로 나가니 한 폴더에 나란히 있다.
- 「PRD」라는 이름을 조각 문서에 쓰지 않는다. 프로젝트의 목표 · 범위는 마스터플랜이 든다.
- `docs/schema.md` 는 다른 레포처럼 데이터 모델(대장 둘)만 든다.
- 착공 때 모르는 것을 지어내 채우라고 틀이 강요하지 않는다 — ERP 의 「짓는 조각이 정한다」가 일반형에 들어온다.
- 대가: kickoff 스킬은 `PRD.md` 를 쓴다 — 계정 스킬의 일로 적는다. ERP 에는 옛 모양(1 ~ 4단계)과 새 모양이 한동안
  함께 있다. `audit-internal` 은 기준 문서로 `PRD.md` 를 찾는다 — 조각 나눔 「틀 배포」가 맡는다.
