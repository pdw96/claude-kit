# 0016 — 설계 → 구현 관문은 claude-kit 의 키 없는 검사와 `vibe-slice` 의 스킬 둘이 문다

2026-10-08 · 결정함 · 여섯 다 저자가 정했다 — 2 는 저자가 세션에 추천을 맡겼고, 4 ~ 6 은 세션이 저장소 규칙에서 끌어내 제안했다. 2 · 4 ~ 6 은 저자가 착공 PR(#32)에서 승인했다

## 맥락

절차 지도는 단계 3(구현)의 들어가는 조건을 「착공 PR 이 머지됐다」로 적었지만 무는 것이 없다 — ADR 0006 이 「강제는
없다」고 적고 조각 나눔 「설계 → 구현 관문」에 넘겼다. 그 자리를 어긴 PR 은 둘이다. 강호쟁패 #1 은 착공 문서와 가설공사 ·
검사 스크립트가 한 PR 이었고(파일 90, 리뷰 12회차), claude-kit #7 은 절차 지도가 서기 전에 기획 · 설계 문서와 비교기 ·
검사기가 한 PR 이었다(파일 16). 절차 지도가 선 뒤 claude-kit 의 구현 PR 다섯(#15 · #18 · #21 · #25 · #29)은 모두 착공이
머지되고 5 ~ 15 분 뒤에 열렸다 — 한 가지에 PR 하나라 순서가 저절로 지켜졌고, 검사가 지킨 것이 아니다.

증거가 난 강호쟁패는 플러그인(`vibe-slice`)만 쓰고 저장소에 `.claude/` 가 없다. ERP 는 사본을 쓴다. claude-kit 의 CI
검사는 두 레포에 닿지 않는다. `eval.yml` 은 수트 지문에 들어 고치면 route 수트가 돈다.

## 대안

1. 무는 자리: **claude-kit 은 키 없는 검사, 다른 레포는 `vibe-slice` 의 스킬(`slice-docs` 가 착공 PR 에 싣는 것을 적고,
   `slice-review` 가 구현 PR 을 가르기 전에 착공 머지를 본다)** / 검사만 — 다른 레포는 「다른 레포의 문서 대조 검사」로 넘긴다 /
   스킬만 / 검사를 `vibe-slice` 에 실어 사본 길로 다른 레포에도 심는다.
2. 검사가 무는 것: **G1 착공 PR 에 구현이 없다 · G2 구현을 바꾸는 PR 은 기준 가지에 설계가 머지된 `진행` 조각이 있다** /
   G1 · G2 에 더해 구현 PR 이 바꾼 파일이 설계 ① 표의 그 PR 줄에 있다(나가는 조건 「⑥ 밖의 것을 싣지 않았다」).
3. 구현 PR 이 어느 조각의 것인지: **기준 가지에 그런 `진행` 조각이 하나라도 있으면 통과** / 커밋마다 `Slice:` 꼬리말 /
   PR 본문의 줄(CI 이벤트로만 읽는다).
4. 결정 문서의 집합(G1 이 착공 PR 에 허락하고, G2 가 구현으로 세지 않는 파일): **의도 문서 · `docs/master-plan.md` ·
   `docs/procedure.md` · `docs/adr/*.md` · `docs/slices/*/requirements.md` · `design.md`** / 조각 폴더와 마스터플랜만 /
   마크다운 전부.
5. 기준과 머리: **인자(`--base` · `--head`) > CI 의 `pull_request` 이벤트 파일의 기준 · 머리 sha — 기준 가지가 기본 가지가
   아니면(쌓은 PR) 기본 가지 > `origin/main` · `main` 가운데 앞선 쪽과의 merge-base 에서 작업트리까지** /
   `GITHUB_BASE_REF` 의 가지 끝 / `eval.yml` 이 sha 를 넘긴다 / 로컬은 `origin/main` 만.
6. 검사를 부르는 자리: **`gates.sh` — 검사와 자체 시험(`test-*.py`) 둘** / `eval.yml` 의 새 스텝.

## 결정

굵은 쪽 여섯. 1 · 3 은 저자가 인터뷰에서 정했다(2026-10-08). 2 는 저자가 「추천해 달라」고 맡겼고 세션이 굵은 쪽을 골랐다.
4 ~ 6 은 세션이 제안했다. 저자가 착공 PR(#32)에서 2 · 4 ~ 6 을 그대로 승인했다(2026-10-08).

- 2 에서 ① 표 대조를 뺀 까닭 — ① 표의 서식을 앵커볼트로 묶어야 하고, 한 칸에 경로 여럿 · 설계 끝 날짜 항목 · 새 ADR 처럼
  ① 에 없는 파일을 싣는 구현 PR(#29 · #30)이 떨어진다. 「⑥ 의 그 줄이 담지 않은 일을 한다」는 이미 `slice-review` 의 안
  갈래다(ADR 0015 의 1).
- 4 는 claude-kit 의 착공 PR 넷(#17 · #20 · #24 · #28)이 바꾼 파일의 합(조각 폴더 · ADR · 마스터플랜 · 절차 지도)에, 범위가
  바뀌면 착공보다 먼저 고치는 의도 문서(「두 층」 「벗어난다」)를 더한 것이다.
- 5 의 `GITHUB_BASE_REF` 는 가지 이름이라, 이벤트 뒤에 기준 가지가 움직이면 merge-base 가 이벤트의 기준과 달라진다.
  `eval.yml` 이 넘기는 길은 수트를 한 번 돌린다. 쌓은 PR 을 기본 가지로 보는 까닭 — 머지되지 않은 착공 가지 위에 구현 PR 을
  쌓으면 그 가지의 마스터플랜에는 `진행` 조각과 설계가 있어 G2 를 지나간다. 기본 가지와 견주면 착공과 구현이 한 diff 가 되어
  G1 로 떨어진다. 로컬에서 `origin/main` 만 보지 않는 까닭 — 이 착공을 쓴 클라우드 세션의 클론은 `origin/main` 이 #14 에
  멈춰 있고 `main` 만 최신이었다. `origin/main` 만 보면 그 사이 머지된 PR 의 파일이 이 PR 의 변경으로 잡혀 거짓 G1 이 난다.
- 6 은 조각 5 · 6 의 자체 시험(`test-sync-slice.py`)과 같은 길이다 — `eval.yml` 을 고치지 않는다.

## 결과

- 1: claude-kit 의 PR 은 검사가, 강호쟁패 · ERP 의 PR 은 스킬이 막는다. 대가 — 다른 레포에서는 세션이 스킬을 부를 때만
  문다. 다른 레포에서 키 없이 무는 것은 조각 나눔 「다른 레포의 문서 대조 검사」의 일로 남는다. 스킬 둘을 고치므로
  `vibe-slice` 의 판이 오른다.
- 2: 단계 2 → 3 의 순서만 문다. 단계 3 의 다른 조건(④ 의 열어 둔 것을 정했나 · 구조 문서를 고쳤나)과 나가는 조건은 사람과
  `slice-review` 가 본다.
- 3: `진행` 조각이 둘 이상이면 다른 조각의 구현을 실어도 지나간다. 조각 밖 PR(조각 사이의 고침)은 `진행` 조각이 없을 때
  떨어진다 — 예외 표지는 없고, 조각 나눔에 줄을 먼저 더한다(「두 층」).
- 4: `docs/procedure.md` 만 고치는 PR 은 조각 밖이어도 지나간다. 의도 문서 줄은 마스터플랜 「가리키는 문서」에서 읽는다.
- 5: 로컬 `gates.sh` 도 커밋 전 작업트리까지 본다. 기준을 못 찾으면(원격 가지가 없다 · 얕은 클론) 떨어진다 — 모르면 지나가지
  않는다.
- 6: `gates.sh` 의 끝 개수가 열넷에서 열여섯이 된다. route 수트는 이 조각의 파일로 돌지 않는다.
