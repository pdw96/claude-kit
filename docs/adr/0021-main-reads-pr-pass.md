# 0021 — `main` 푸시가 머지된 PR 의 merge ref 캐시를 목록 API 로 읽어, 같은 지문이면 수트를 건너뛴다

2026-10-12 · 결정함 · 1 ~ 3 은 저자가 착공 전 인터뷰에서 정했다. 4 는 세션 제안 — 저자 승인 대기

## 맥락

`eval.yml` 은 통과한 수트 지문(`eval-key.py route`)을 Actions 캐시에 적고, 같은 지문을 다시 만나면 eval 잡을 건너뛴다. 캐시는 실행의 ref
범위에 적힌다 — PR 실행은 `refs/pull/<N>/merge` 에 적고 그 PR 의 실행만 그것을 읽는다. `main` 푸시는 `main` 범위만 읽는다. 그래서 지문을
바꾸는 PR 은 PR 에서 한 번, 머지 뒤 `main` 에서 같은 키로 한 번 더 돈다 — 조각 11 성공 기준 6 이 이것으로 못 미쳤다(#49 머지 8734f58,
run 38221927726). `main` 푸시 51 가운데 eval 잡이 돈 것이 19 이고, 파일 쪽 지문이 바뀐 머지 13 은 다 돌았다(2026-10-12 에 셌다). route 수트
한 번은 30회다.

`main` 푸시가 `main` 범위에 적는 것은 그대로 필요하다 — 다음 PR 들은 `main` 범위를 읽는다. 바뀌어야 하는 것은 `main` 푸시가 「통과했다」를
알아보는 근거다. 캐시 restore 는 다른 ref 범위를 읽지 못하지만, 캐시 목록 API(`GET /repos/{o}/{r}/actions/caches`)는 저장소의 모든 ref 의
항목을 `key` · `ref` 로 보여 준다.

## 대안

1. 근거를 찾는 길: **`main` 푸시의 gate 잡이 캐시 목록 API 로 머지된 PR 의 merge ref 에 같은 키가 있는지 본다** / PR 실행이 끝나면
   `workflow_run` 워크플로(기본 가지 문맥)가 그 키를 `main` 범위로 옮겨 적는다 / PR 의 eval 잡이 통과한 키를 아티팩트로 올리고 `main` 푸시가
   그 PR 의 실행에서 내려받아 견준다 / 고치지 않고 감수한다.
2. 믿는 범위: **그 푸시를 머지 커밋으로 가진 PR 하나의 merge ref 만** / 거기에 더해 그 PR 의 head 가 이 저장소의 가지일 때만 / 어느 ref 든
   같은 키면.
3. 판정의 자리: **수트 지문 밖 스크립트 하나와 그 자체 시험 · 변조본을 `gates.sh` 가 부르고, `eval.yml` 은 부르는 줄과 권한만** / `eval.yml`
   스텝 안에 `gh` 로 몇 줄.
4. 머지 전에 볼 길: **PR 실행에서 같은 API 두 곳을 읽어 보기만 한다(판정에 쓰지 않는다)** / 머지 뒤 첫 `main` 푸시에서야 본다.

## 결정

굵은 쪽 넷. 1 ~ 3 은 저자가 착공 전 인터뷰에서 정했다(2026-10-12) — 셋 다 세션이 추천한 쪽이다. 4 는 세션이 제약(판정은 `main` 푸시에서만
쓰여 머지 전에 실물에 대어 볼 수 없다)에서 끌어내 제안했다.

- 1 은 저장소를 캐시 하나로 둔다 — 「통과한 실행만 적는다」는 지금의 규칙이 그대로 근거가 된다. `workflow_run` 은 워크플로 파일이 하나
  늘고, 옮겨 적는 실행과 `main` 푸시가 머지 직후 앞뒤를 다툰다. 포크에서 온 `workflow_run` 은 캐시 쓰기가 막혔다(GitHub 변경 공지
  2026-06-26). 아티팩트는 PR 의 실행들을 찾아 내려받고 풀어야 해 코드가 가장 많다. 감수하면 키를 바꾸는 PR 마다 30회가 더 나간다.
- 2 는 리뷰되고 머지된 그 PR 이 적은 것만 믿는다. `pull_request` 실행은 포크에서도 제 merge ref 범위에 캐시를 쓸 수 있어, 어느 ref 든 믿으면
  포크 PR 이 제 워크플로로 적어 둔 키를 `main` 이 믿는다. 같은 저장소 가지로 좁히는 안은 포크 PR 을 늘 `main` 에서 다시 돌리는데, 머지된
  포크 PR 의 워크플로도 머지 전 리뷰가 본다 — 지금 쓰기 권한자는 저자 한 명이다(`eval.yml` 149 ~ 155 줄).
- 3 은 `CLAUDE.md` 「작업 방식」(새 검사를 세우면 변조본으로 떨어지는 것을 함께, 키 없이 도는 목록은 `gates.sh` 한 군데)과 조각 11 의 교훈을
  따른다 — `eval.yml` 안의 판정은 고칠 때마다 수트 지문이 바뀌고, 키 없이 무는지 볼 길이 없다. 판정이 틀리면 수트를 건너뛰어 아무도 모르므로
  무는지를 보는 것이 이 조각의 중심이다.
- 4 는 권한 · 응답의 꼴이 틀렸을 때 그것을 머지 뒤에야 알면, 고치는 PR 이 `eval.yml` 을 다시 고쳐 수트가 한 번 더 돈다. 읽어 보기는 판정에
  쓰지 않아 틀려도 동작이 같고, 실패는 경고뿐이다.

## 결과

- 1: 지문을 바꾸는 PR 의 수트가 PR 에서 한 번만 돈다. `main` 푸시는 근거를 찾으면 같은 키를 `main` 범위에도 적는다. 대가 — gate 잡이 API 를
  두 번 부르고, 토큰에 `actions: read` · `pull-requests: read` 가 든다. API 를 못 읽으면 지금처럼 돈다.
- 2: 직접 푸시 · PR 여럿을 담은 푸시는 지금처럼 돈다. 대가 — PR 이 제 워크플로를 고쳐 거짓 키를 적은 것은 리뷰가 막는다. 판정은 그것을
  가르지 못한다.
- 3: `gates.sh` 가 스물둘에서 스물넷이 된다. 판정을 고쳐도 수트가 돌지 않는다. 대가 — 판정의 조건이 `eval.yml` 이 아니라 스크립트에 있어
  워크플로만 읽고는 전부를 모른다 — `eval.yml` 의 스텝 주석이 그 파일을 가리킨다.
- 4: 머지 전에 B 의 로그에서 권한과 응답의 꼴을 본다. 대가 — PR 실행마다 API 두 번.
- `main` 에서 다시 돌리려면 `main` 범위 항목과 머지된 PR 의 항목을 둘 다 지우거나 `workflow_dispatch` 를 부른다.
