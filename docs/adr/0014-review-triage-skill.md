# 0014 — 리뷰 지적은 `vibe-slice` 의 스킬 `slice-review` 가 세 갈래로 가른다

2026-10-07 · 결정함 · 일곱 다 저자가 정했다 — 4 ~ 7 은 세션이 저장소 규칙에서 끌어내 제안했다

## 맥락

절차 지도는 리뷰 지적을 설계 ② · ③ 에 비춰 「안」(고친다)과 「밖」(답글)으로 가르라고 한 문단만 적었다. claude-kit 은 그대로
갈랐는데 PR #14 ~ #27 의 지적 88 건 가운데 밖은 4 건뿐이었고, 리뷰 한도를 넘긴 PR 이 다섯이었다. 88 건 가운데 29 건은 설계가 그
경계를 말하지 않은 것이고 19 건은 ⑤ 가 ② 를 대어 보지 않은 것이다 — 두 갈래로는 말하지 않은 경계가 다 「안」이 되어, 리뷰가
회차마다 한 칸씩 채웠다(조각 6 요구사항 「문제」). 착공 PR 은 설계 자체가 리뷰 대상이라 비춰 볼 ② 가 없고, 회차가 가장
길었다. ERP 는 점수 · 문턱 · 쏠림 신호 · 방안 A ~ E 를(`docs/리뷰-루프.md`), 강호쟁패는 P0 ~ P2 병합 기준(ADR-0005)을 따로 세웠다.

## 대안

1. 가르는 축: **세 갈래 — 안 · 밖 · 말하지 않음** / 두 갈래(지금 문단) / ERP 점수제(실결함 · 회귀 · 기존 한계 · 가상 입력)를
   일반형으로.
2. 싣는 자리: **`vibe-slice` 의 둘째 스킬** / `slice-docs` 안의 절 / 절차 지도의 문서만 / 리뷰어 쪽(`AGENTS.md` 에 설계 ② 의
   보장하지 않는 것을 옮긴다).
3. 멈춤: **쏠림 신호 하나** / ERP 의 점수 · 문턱 · 방안을 그대로 / 정하지 않는다(리뷰 한도와 소유자 판정만).
4. 규칙의 원천: **스킬의 `SKILL.md` — 절차 지도는 가리킨다** / 절차 지도에 두고 스킬이 URL 로 가리킨다 / 두 곳에 둔다.
5. 스킬 이름: **`slice-review`** / `review-triage` / `review-loop`.
6. 착공 PR 의 기준: **의도 문서의 What · Not, 그 조각 요구사항의 「하지 않을 일」, 절차 「…의 칸」 — 설계를 짚은 지적에는
   같은 PR 요구사항의 성공 기준 · 제약도** / 착공 PR 은 가르지 않는다 /
   리뷰 중인 설계 ② 를 그대로 기준으로.
7. 사본 길: **`sync-slice.sh` 가 `vibe-slice/skills/` 의 스킬을 다 심는다** / 심을 스킬을 인자로 받는다 / 스킬마다 스크립트.

## 결정

굵은 쪽 일곱. 1 ~ 3 은 저자가 인터뷰에서 정했다(2026-10-07). 4 ~ 7 은 세션이 이 저장소의 규칙에서 끌어내 제안했고, 저자가
착공 PR(#28)을 연 뒤 둘째 인터뷰에서 넷 다 승인했다(같은 날).

- 4 는 「같은 목록을 두 군데 두면 갈린다」(`CLAUDE.md`). 틀과 달리 리뷰 규칙은 세션이 리뷰가 올 때마다 읽어야 하는데, 절차
  지도는 URL 로만 닿아(ADR 0013 의 2) 네트워크가 막힌 세션이 가르지 못한다. 갈래의 정의는 `SKILL.md`(호출 시 ≤ 4,500 자)에
  들고, 넘치는 꼴(회차 표 · 답글)은 같은 스킬 폴더의 옆 파일로 뺄 수 있다 — 스킬 폴더가 한 군데라는 것은 그대로다(#28 Codex
  2 회차 뒤 세션이 더했다).
- 5 는 이미 있는 `slice-docs` 와 같은 앞가지 — `/vibe-slice:` 아래 둘이 같은 조각 절차의 도구로 읽힌다.
- 6 은 절차 지도의 들어가는 조건에서 왔다 — 착공 PR 이 지켜야 하는 것은 단계 0 의 「의도의 What 안 · Not 밖」, 단계 1 · 2
  의 나가는 조건(「…의 칸」)이다. 리뷰 중인 설계를 기준으로 쓰면 리뷰가 고치자는 그 문서로 지적을 가르게 된다.
- 7 은 조각 5 의 C1 ~ C5 를 그대로 넓힌다. 인자로 고르게 하면 ERP 가 스킬 하나만 받아 둘의 판이 갈린다.

## 결과

- 1: 「말하지 않음」은 바로 고치지 않고 같은 갈래를 전수로 찾은 뒤 경계를 정하고, 그 결정을 남긴다(구현 PR 은 설계 끝의
  날짜 항목, 착공 PR 은 그 PR 의 설계 ② · ③, 닫는 PR 은 그 PR 의 「닫으며」 안 — 조각 6 설계 S3) — 그다음 회차에 같은 갈래가 다시 기준으로 갈린다. 사실의 틀림(어긋남 · 재현되는 결함)은 경계가 아니다 — 이 PR 이 들이거나
  건드린 자리면 「안」, 건드리지 않은 자리의 기존 결함이면 「밖」이다(조각 6 설계 S2, #28 Codex 2 회차). 대가 —
  지적 하나에 드는 일이 는다(전수 찾기 · 날짜 항목). ERP 의 「가상 입력」은 따로 두지 않는다 — 검사 장치의 받지 않는 입력은
  ③ 이 닫힌 목록으로 들어 「밖」이 된다.
- 2: 강호쟁패는 `vibe-slice` 갱신으로, ERP 는 `sync-slice.sh` 로 받는다 — 조각 5 의 두 길 그대로다. 대가 — 앵커볼트 이름이
  하나 늘고, `vibe-slice` 의 설명이 「문서 틀 넷」보다 넓어진다. 리뷰어 쪽은 고치지 않아 리뷰 봇은 여전히 기준 밖을 짚는다 —
  그것을 「밖」으로 답하는 것이 이 스킬의 일이다.
- 3: 같은 변경 단위를 두 회차 연속 짚고, 두 회차 합쳐 그 단위의 지적이 셋 이상이며 두 회차 지적의 과반이면 멈추고 소유자에게
  묻는다(ERP 쏠림 신호의 조건 그대로 — 조각 6 설계 S4). 대가 — 점수 추이가 없어
  회차의 무게를 숫자로 견주지 못한다. 회차 표의 안 · 밖 · 말하지 않음 · 반박됨의 수가 그 자리를 대신한다. ERP 는 제 규칙을 계속 쓴다.
- 4: `docs/procedure.md` 「4 에서 지적은 설계에 비춰 가른다」 문단은 스킬을 가리키는 줄로 준다. 대가 — 절차 지도만 읽는
  사람은 가르는 법을 스킬 파일에서 읽어야 한다.
- 6: 착공 PR 의 말하지 않음은 그 PR 의 설계 ② · ③ 에 바로 쓴다 — 아직 머지되지 않은 문서라 날짜 항목이 필요 없다.
  설계를 짚은 지적에는 같은 PR 요구사항의 성공 기준 · 제약도 기준으로 더했다 — 그것을 빼면 제 요구사항을 채우지 못하는
  설계가 「말하지 않음」으로 빠져나간다(#28 Codex 1 회차 — 저자가 이 넓힘을 승인했다). 「…의 칸」은 `slice-docs` 의 틀에서
  읽어 네트워크 없이 닿는다.
- 7: 이미 `slice-docs` 사본이 있는 ERP 는 `--force` 로 다시 심어야 `slice-review` 를 받고, 그때 `slice-docs` 사본도 이 커밋의
  것으로 덮인다.
