# 0050 — 회수율은 담당 감사자가 놓친 실제 결함으로, 수트 문턱 밖에서 잰다

2026-10-27 · 결정함 · 1 ~ 3 은 저자가 이 착공 세션에서 정했다(세션이 순서 없는 후보 다섯의 꺼낼 조건을 대 보이고 저자가 세션이 추천한 「회수율 측정」을 골랐고,
이어 재료 · 문턱 · 규모를 물어 저자가 세션이 추천한 쪽을 골랐다). 4 ~ 8 은 세션이 제안했고 착공 PR 에서 저자가 본다

## 맥락

수트는 오검율과 트리거 정확도를 재고, 회수율은 재지 않는다 — 지어낸 결함은 단정한 것의 픽스처 판이라서다(`vibe-audit/evals/README.md` 「오검율」 · 「재지 않는
것」). 조각 「남은 결함 넷」은 회수 쪽 함정을 세 판 만들었고, 수트 모델은 그만큼 노골적인 자리를 옛 문구로도 잡았다(ADR 0028 의 맥락).

ERP 대장(`pdw96/ERP` `main` `37c77b4`)에는 NC 가 227 줄 있고, 196 줄은 감사 회차가 냈다. 그 밖의 줄 가운데에는 **담당 감사자가 이미 감사한 커밋에 있던 결함**을
다른 리뷰가 찾은 것이 있다 — NC-104 · NC-102(`audit-data` ⑧ 의 `bb8c3db`), NC-74(`audit-contract` ⑧ 의 같은 커밋), NUL 과 꺼진 공통코드(㊱ · ㊲ 의 `b5af763`).
조각 39 설계 ③ B 가 후보와 확인한 것을 든다.

러너(`run-evals.sh`)는 고정했고(같은 README 「고정한 것」), 결과 정리가 수트 자리를 `vibe-audit/evals` 로 박아 둔다. 하네스 `claude plugin eval` 은 `--eval-dir` 로
플러그인 아래 다른 폴더의 케이스를 돌릴 수 있다(CLI 2.1.311 의 도움말). CI 의 전수는 인자 없이 기본 폴더를 돌고 문턱 0.8 을 건다(`eval.yml`).

## 대안

1. 재료: **담당 감사자가 놓친 결함(다른 리뷰가 찾은 것)** / 감사 회차가 찾은 결함 / 둘을 같은 수로.
2. 문턱: **수트 verdict 밖 — 재기만 하고 기준선을 남긴다** / 전수의 문턱(0.8)에 넣는다.
3. 규모: **케이스 여섯 · 로컬 측정 $30** / 셋 · $15 / 열 · $50.
4. 자리: **`vibe-audit/recall/` — 러너가 `--eval-dir` 을 받는다** / `vibe-audit/evals/` 안에 `recall-*` 접두로 두고 `eval.yml` 의 전수가 그것을 빼게 / 플러그인 밖 폴더.
5. 수트 지문: **회수율 폴더는 두 모드(route · full) 밖** / route 만 밖 / 둘 다 안.
6. 목적 그레이더: **결정론 정규식 하나(`recall-found`) — 표본 필수** / 심판.
7. 대조군: **두지 않는다** / 판정 케이스처럼 `real-nc-found` 를 둔다.
8. PR 나눔: **B(러너 · 검사 · 지문 · 첫 케이스) · C(남은 다섯) · D(기준선 · 문서)** / 한 PR / 케이스마다 한 PR.

## 결정

굵은 쪽 여덟.

- 1 은 찾았던 결함을 옮기면 「찾았던 것을 다시 찾는가」가 되어 대개 지나가기 때문이다 — 회수 쪽 함정 세 판이 그렇게 끝났다(ADR 0028). 놓친 결함은 감사자의 문구와
  모델로 한 번 못 잡은 자리라 숫자가 움직일 여지가 있다. 저자가 골랐다. 대가 — 놓친 증거가 있는 감사자만 잰다(`audit-data` · `audit-contract`).
- 2 는 놓친 결함을 지금 감사자도 놓칠 수 있고, 그것이 재려는 사실이기 때문이다 — 문턱에 넣으면 전수가 늘 빨강이거나, 초록을 위해 문구를 고치는 일이 이 조각에 실린다.
  첫 숫자를 본 뒤에야 문턱을 정할 근거가 선다. 저자가 골랐다. 대가 — 회수가 떨어져도 머지는 막히지 않는다. 보이는 자리는 PR 본문과 기준선이다.
- 3 은 두 감사자에 걸친 후보가 여섯이고(설계 ③ B 의 R1 ~ R6), 여섯 × 세 회차가 감사 한 번씩이라 측정 한 판이 $30 안에 든다고 봤기 때문이다. 저자가 골랐다.
- 4 는 하네스가 이미 폴더를 가르고, 전수 · route 가 아무것도 고치지 않아도 회수율 케이스를 모르게 되기 때문이다. 접두로 두면 `eval.yml` 이 빼는 글을 들어야 하고,
  `--case` 는 고르는 글롭이라 빼는 꼴이 없다. 플러그인 밖에는 `--eval-dir` 이 닿지 않는다. 대가 — 고정한 러너에 깃발 하나와 끝의 줄을 더한다. 새 방어가 아니라
  지금의 결과 정리를 그 폴더에 대는 것이고, 받는 값은 닫힌 목록이다(조각 39 설계 ③ A).
- 5 는 회수율 케이스를 route 도 전수도 돌리지 않기 때문이다 — 그 파일만 바꾼 PR 이 수트를 다시 돌릴 까닭이 없다. 러너는 두 모드에 그대로 든다.
- 6 은 「그 결함이 NC 절에 있는가」가 무엇을 찾는지 정확히 아는 질문이기 때문이다 — 결정론이 낫다(`vibe-audit/evals/README.md` 「심판」). 표본을 필수로 하는 것은 정규식이
  그 결함을 실제로 가르는지 키 없이 보이려는 것이다.
- 7 은 심은 결함이 곧 실제 결함이라, 아무것도 내지 않는 감사자가 `recall-found` 에서 이미 떨어지기 때문이다. 대조군이 지키던 자리가 목적 그레이더와 겹친다.
- 8 은 모양 검사와 변조본이 물 실물로 첫 케이스가 B 에 있어야 하고, 기준선은 여섯이 다 든 원본에서 한 번 재야 하기 때문이다.

## 결과

- 1: 케이스의 `case.yaml` 이 출처(대장의 자리 · 감사한 커밋 · 찾은 쪽)를 든다. 다른 감사자의 회수율은 놓친 증거가 생기면 조각 나눔의 새 줄로 꺼낸다.
- 2: 기준선이 `docs/eval-log/` 와 `vibe-audit/evals/README.md` 「회수율」에 남는다. 문턱을 걸지는 따로 정한다.
- 4: `run-evals.sh --eval-dir recall` 이 지금의 결과 정리를 그대로 하고 끝에 회수 줄을 찍는다. 그 밖의 값은 종료 2.
- 5: 회수율 케이스만 고친 PR 은 route 수트를 돌리지 않는다.
- 6 · 7: `verify-evals.py` · `verify-graders.py` 가 회수율 케이스에 목적 그레이더 하나 · `auditor-fired` · 표본을 요구한다. `bite-gates.sh` 가 그것을 문다.
- 8: 되돌리면 D · C · B 를 차례로 되돌린다.
