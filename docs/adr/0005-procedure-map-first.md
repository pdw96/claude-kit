# 0005 — 절차는 지도를 먼저 그리고, 변경 관리 구현은 그다음 조각에

2026-10-06 · 결정함

## 맥락

강호쟁패 #1 · #3 과 ERP #84 에서 리뷰 회차가 끝나지 않았다(PRD 조각 2 「문제」). 저자는 통상 IT 구축(SI)의
기획 → 설계 → … 절차를 바이브코딩에 들이고 싶어 했고, 인터뷰에서 SI 절차를 kick-off 전후로 펼쳐 바이브코딩과
견줬다. 빈자리가 일곱 나왔는데 증거가 있는 것은 변경 관리 · 설계 문서(PR 일곱)와 단계 구분(PR 하나)뿐이다.

## 대안

1. **변경 관리부터 구현** — ERP `리뷰-루프.md` 의 일반형을 플러그인으로 세우고 강호쟁패에 심는다. 설계 문서
   틀은 분류의 기준이라 함께 든다. PR 2~3, eval 비용.
2. **절차 지도부터** — kick-off 전후 전체를 문서로 정의하고 기획 · 설계 틀을 둔다. 문서만, $0. 변경 관리는
   로드맵 첫 칸.

## 결정

**2 — 지도부터.**

## 결과

- 저자의 처음 의도(절차 전체를 들인다)에 가깝다. 1 은 일곱 빈자리 중 하나를 메우고 나머지 그림이 없다.
- 「설계를 먼저, 자기 PR 로」를 이 결정 자체에 적용한다 — 지도가 설계이고 리뷰 루프가 구현이다.
- 대가: 이 조각이 끝나도 회차는 줄지 않는다. 지도는 강제하지 않는다. 그것을 지도 머리에 적어, 물지 않는 문서를
  게이트처럼 보이게 두지 않는다.
- 위험: 써 보기 전에 지어낸 절차가 된다. 증거 없는 빈자리에 규칙을 두지 않는 것(PRD 하지 않을 일 6)과, 지도를
  세 사례에 대 보는 역검증(설계 ⑤)으로 막는다.
