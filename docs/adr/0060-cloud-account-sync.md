# 0060 — 앱에서 연 클라우드 세션은 계정 동기화로 원본을 받고, 레포 사본은 특화가 있는 레포에만 둔다

2026-10-30 · 결정함 · 1 · 2 · 3 은 저자가 조각 47 의 착공 세션에서 정했다(세션이 세 갈래씩 보이고 물었다 — 1 · 2 는 세션이 추천한 쪽이 아닌 것을 저자가
골랐다). 3 은 세션이 처음 도구로 연 ERP 세션에서 동기화가 일어나지 않아(아래 「맥락」의 셋째 줄), 저자가 앱에서 ERP 세션을 열어 잰 것으로 채웠다.
4 ~ 6 은 세션이 제안했고 착공 PR 에서 저자가 본다.

## 맥락

`README.md` 「설치 — 경로가 둘인 이유」는 저장소가 `.claude/settings.json` 에 마켓플레이스를 선언하는 길(`extraKnownMarketplaces` · `enabledPlugins`)이 열린 버그
셋을 달고 있어 「대화형 세션은 마켓플레이스로, 클라우드 레인은 레포 사본으로」 받는다고 적는다. 2026-10-30 에 그 셋을 다시 봤다 — anthropics/claude-code#78119
(클라우드에서 저장소 선언을 무시)는 열려 있고, #32606 · #13097 은 수정 없이 봇이 not planned 로 닫았다. 계정 플러그인이 클라우드 세션에 오지 않는다는 #92031 도
열려 있다(마지막 실패 보고 2.1.283).

그런데 같은 날 세 세션을 재니 저장소 선언과 다른 길이 열려 있었다. 셋 다 같은 계정 · 같은 환경(`cloud_default`) · CLI 2.1.314 다.

| 세션 | 연 곳 | `CLAUDE_CODE_SYNC_PLUGINS` | `~/.claude/plugins/synced/` | 뜬 것 |
|---|---|---|---|---|
| claude-kit(이 착공 세션) | 앱(`desktop_app`) | `1` | `vibe-slice` 0.9.0 · `vibe-audit` 0.4.6 — `marketplaceKind: account_marketplace`, `marketplaceName: claude-kit` | 동기화본만 — `vibe-audit:audit-*` · `vibe-slice:slice-docs` 따위. 이 저장소에는 사본이 없다 |
| ERP(세션이 도구로 연 세션) | `create_session`(`claude_code_mcp_seed`) | 없음 | 빈 폴더 | 사본만 — `audit-*` 여섯 · `audit-brief` · `slice-docs` · `slice-review` |
| ERP(저자가 앱에서 연 세션) | 앱 | `1` | 동기화본 | **두 벌** — `audit-data` 와 `vibe-audit:audit-data` 따위, 감사자 여섯 · `slice-docs` · `slice-review` · `audit-brief` 가 다 둘씩. 스코프 없는 `slice-docs` 는 `/home/user/ERP/.claude/skills/slice-docs`(사본)로 가고, 동기화본은 `vibe-slice:slice-docs` 로만 불린다 |

세 세션 다 `SKIP_PLUGIN_MARKETPLACE=true` 다 — 저장소 선언은 여전히 건너뛴다. 동기화본의 글은 `main` 과 같았다(YAML 머리말의 표기만 다르다). 같은 계정에서도
세션을 어디서 열었는지에 따라 동기화가 갈렸다. 세션 중간에 레포를 붙여 등록해도(`register_repo_root`) 그 레포의 사본은 실리지 않았다 — 처음 연 레포의 목록 그대로다.

사본 레포는 둘이다(`copies.json`). 후보 대장(`feedback.json`)에서 ERP 는 특화(`specific`) 판정이 24 건이고, 강호쟁패는 후보가 없다. ERP 사본은 원본과 감사자마다
10 ~ 41 줄 다르다(심은 커밋 `ddcd21f` 뒤로 원본이 나아간 몫과 특화가 섞여 있다).

## 대안

1. 배포 갈래: 계정 동기화를 셋째 경로로 적고 사본은 그대로 둔다 / **셋째 경로로 적고, 레포 사본은 특화가 있는 레포에만 둔다** / 경로는 둘로 두고 README 의 버그 표와
   「클라우드 레인은 받지 못한다」만 고친다.
2. 사본 레포의 겹침: `sync-agents.sh` 가 심는 `.claude/agents/README.md` 와 원본 README 에 「스코프 없는 이름이 사본」이라고 적는다 / 원본 README 에만 적는다 /
   **동기화본을 레포 쪽에서 끄는 법부터 재고, 되면 그 법을 적는다**.
3. 근거를 언제 잴까: **착공 세션에서 ERP 세션을 열어 잰다** / 구현 첫 PR 에서 / 저자가 재어 알려 준다.
4. 「특화가 있는 레포」를 가르는 기준: **후보 대장에 그 레포의 `specific` 판정이 하나 이상 있다** / 사본이 원본과 다르다(`verify-copy.py` FAIL) / 그 레포가 스스로 정한다.
5. 끄는 법을 잴 자리: **claude-kit 의 버리는 가지 — 머지하지 않고 지운다 — 를 저자가 앱에서 연 세션** / 사본 레포(ERP)의 가지 / 재지 않고 후보만 적는다.
6. 끄는 법이 없을 때 README 가 적는 것: **두 벌이 뜬다는 것과 부르는 이름(스코프 없는 이름은 사본, `vibe-audit:` · `vibe-slice:` 를 붙인 이름은 동기화본)** / 계정
   설정에서 동기화를 끄라고 적는다 / 조각을 닫지 않고 기다린다.

## 결정

1. **세 경로로 적는다 — 로컬 대화형 세션은 마켓플레이스, 앱에서 연 클라우드 세션은 계정 동기화, 레포 사본은 특화가 있는 레포와 동기화가 닿지 않는 세션의 몫.**
   특화가 없는 레포는 사본을 심지 않아도 원본을 받는다. `INTENT.md` What 의 배포 줄이 바뀐다 — 마스터플랜 「범위 변경」에 적는다.
2. **겹침은 끄는 법부터 잰다.** 사본 레포의 세션에 원본과 특화 사본이 같은 설명으로 함께 뜨면, 이름을 부르지 않고 설명으로 고를 때 원본이 잡힐 수 있다 — 그러면 특화가
   빠진다. 레포 쪽 설정으로 동기화본을 끌 수 있으면 그 법을 적어 사본 레포가 고른다.
3. **근거는 착공 세션에서 앱으로 연 ERP 세션이다.** 도구로 연 세션은 동기화를 받지 않아 저자가 앱에서 쟀다(「맥락」의 표).
4. **기준은 후보 대장의 `specific` 판정이다.** 저자가 한 판정이라 레포의 말과 원본의 말을 이미 갈랐다. 사본이 원본과 다르다는 것은 심은 뒤 원본이 나아가도 참이라 특화의
   증거가 아니다. 판정이 없는 레포가 특화를 세우려면 사본을 심고 고친 뒤 비교기가 낸 후보를 저자가 `specific` 으로 가른다 — 지금의 흐름 그대로다.
5. **끄는 법은 claude-kit 의 버리는 가지에서 잰다.** 사본 레포를 고치지 않는다(`INTENT.md` Not 4). 끄는 것이 되는지는 사본의 유무와 상관없이 동기화본이 사라지는지로
   보인다. 도구로 연 세션은 동기화를 받지 않으므로 그 가지의 세션은 저자가 앱에서 연다.
6. **끄는 법이 없으면 두 벌과 부르는 이름을 적는다.** 2026-10-30 ERP 실측이 이름의 갈림을 보였다. 계정 설정으로 끄면 모든 레포에서 꺼져 1 이 무너진다.

## 결과

- 강호쟁패는 4 의 기준으로 특화가 없는 레포다. 사본을 걷을지는 그 레포가 정한다(`INTENT.md` Not 4). 걷기 전까지 `copies.json` 의 줄은 그대로다.
- 사본이 없는 레포에서 드러난 감사자 결함은 비교기(`compare-copies.py`)에 잡히지 않는다 — 비교기는 사본과 원본의 차이를 본다. 그런 결함은 원본의 결함이므로 원본에서
  고치고 케이스를 붙인다(`CLAUDE.md` 「작업 방식」의 되먹임 규칙). 이 결과를 무는 장치는 없다.
- 감사자 README 를 고치므로 `vibe-audit` 판이 오르고, `vibe-audit/.claude-plugin/plugin.json` 이 수트 지문에 들어 구현 PR 에서 route 수트가 한 번 돈다.
- 동기화가 닿는 조건은 업스트림이 정한다. 잰 것은 앱에서 연 세션과 도구로 연 세션 둘이다 — 나머지(웹에서 연 세션 · 예약 작업 · CI)는 재지 않았다고 적는다.
