# 데이터 모델

이 저장소의 「데이터」는 대장 두 개다. 화면은 없다 — 사람이 읽는 것은 스크립트 출력과 이 파일이다.

## 대상과 관계

| 대상 | 무엇 | 키 | 사는 곳 |
|---|---|---|---|
| **사본** | 대장의 한 줄 — 레포 · 경로 · 심을 때의 커밋 · 날짜 | `repo` | `copies.json` (있음) |
| **차이** | 사본 감사자 파일 하나에서 원본과 다른 덩어리 하나 | (사본, 견준 사본 커밋, 파일, 내용 해시) | 저장하지 않는다 — 스크립트가 매번 계산 |
| **후보** | 같은 내용 해시를 가진 차이를 묶은 것 | `id`(`FB-n`), `hash` | `feedback.json` (새로) |
| **되먹임** | 결함으로 판정된 후보가 원본에 들어간 기록 | 후보와 1:1 | 후보 줄의 `feedback` |

```
사본 1 ── N 차이 N ── 1 후보 1 ── 0..1 되먹임 1 ── 1..N eval 케이스
```

대장 경로 한 줄처럼 같은 문구가 감사자 여섯에 다 있으면 **후보 하나**다. 다른 사본 레포에서
같은 문구가 나와도 같은 후보다 — 두 레포가 따로 같은 말을 썼다면 그것이 곧 「다른 레포에서도
같은 말」의 증거다.

## 차이를 뽑는 법

- **원본 쪽:** `git show <synced_commit>:vibe-audit/agents/<이름>.md` — 원본의 HEAD 가 아니라
  **심을 때의 커밋**과 견준다. HEAD 와 견주면 원본이 그 뒤 움직인 것이 사본의 차이로 보인다.
- **사본 쪽:** 사본 레포의 `HEAD` 에 커밋된 파일. 작업트리가 아니다.
- **견주기 전에 멈추는 경우**(ADR 0003): 사본 레포가 원격 기본 가지보다 뒤다 · 사본 자리
  (`agents_path`)에 커밋 안 된 변경이 있다 · 감사자 파일이 디스크에는 있는데 HEAD 에 없다(무시됨) ·
  대장의 `synced_commit` 이 이 저장소에 없다.
- **걸러내는 것:** `sync-agents.sh` 가 프론트매터 뒤에 넣는 출처 주석 줄(`<!-- pdw96/claude-kit@… -->`)과
  그 뒤 빈 줄, 공백만 다른 줄. **정규화한 줄로 견준다** — 날 줄로 견주면 뜻이 바뀐 줄 옆의 공백
  변경이 한 덩어리로 묶여 해시가 달라진다. 빈 줄은 견줄 목록에서 빠진다.
- **견주는 파일:** 그 커밋의 `vibe-audit/agents/*.md` 에 있는 이름만. 사본에만 있는 파일
  (`.claude/agents/README.md` 등)은 후보가 아니다 — 하지 않을 일 5.

## 내용 해시

덩어리의 **원본 쪽 줄(`-`)과 사본 쪽 줄(`+`)을 둘 다** 넣는다. 지운 것만 있는 덩어리(사본이
원본 문구를 덜어낸 자리)도 후보이기 때문이다.

```
줄들 = ["-" + 줄 for 줄 in 정규화(원본 쪽)] + ["+" + 줄 for 줄 in 정규화(사본 쪽)]
hash = "sha256:" + sha256("\n".join(줄들))
정규화 = 앞뒤 공백 제거 · 연속 공백을 하나로 · 빈 줄 제거
```

구현은 `scripts/compare-copies.py` 의 `content_hash` 다. 둘이 갈리면 그쪽이 참이고 여기를 고친다.

줄 번호는 넣지 않는다 — 위에 문단이 하나 생겨도 같은 후보다(ADR 0002). 사본이 문구를 고치면
새 후보가 되는데, 뜻이 바뀌었을 수 있으니 다시 보는 것이 맞다.

## `feedback.json`

```json
{
  "candidates": [
    {
      "id": "FB-1",
      "hash": "sha256:<64 hex>",
      "seen": [{"repo": "erp", "files": ["audit-secrets.md"], "commit": "<40 hex>", "base": "<40 hex>"}],
      "status": "defect",
      "reason": "다른 레포에서도 같은 말인 근거, 또는 이 레포에서만 참인 이유",
      "decided_at": "2026-10-05",
      "feedback": {"commit": "<40 hex>", "cases": ["handoff-root-cause"], "budget_delta": 412}
    }
  ]
}
```

| 칸 | 뜻 | 규칙 |
|---|---|---|
| `id` | `FB-n` | 1 부터 이어지고 겹치지 않는다. **대장의 지난 판에 있던 번호는 사라지지 않고 hash 도 안 바뀐다** — 판정은 고치되 줄은 지우지 않는다 |
| `hash` | 위의 내용 해시 | 대장 안에서 하나뿐 |
| `seen[].commit` | 판정할 때 견준 사본 커밋 | 40자 |
| `seen[].base` | 그때 견준 원본 커밋(= 그때의 `synced_commit`) | 이 저장소에 있어야 한다 |
| `status` | `specific` 특화 · `defect` 결함 · `hold` 보류 · `fed_back` 되먹임 완료 | 미판정은 대장에 **없는 것**이다 |
| `reason` | 판정 근거 | 비면 안 된다 |
| `feedback` | `fed_back` 일 때만 | `commit` 은 이 저장소에 있고, `cases` 는 **그 커밋의** `vibe-audit/evals/<케이스>/case.yaml` 로 있어야 한다. `budget_delta` 는 그 커밋에서 `verify-budget.py` 가 잰 호출 시 문자 증감 |

**일반 규칙과 특화가 한 덩어리에 섞이면**(`audit-data` 항목 3 처럼) `defect` 로 두고, `reason` 에
일반형으로 옮길 부분을 적는다. 특화 부분은 사본에 그대로 남는다 — 상태를 따로 두지 않는다.

`feedback.commit` 은 머지 커밋 방식(지금의 PR 머지)에 기댄다. 스쿼시로 머지하면 그 커밋이
사라져 대장 검사가 떨어진다.

## 이 모양을 무는 것

`scripts/verify-feedback.py` 가 위 「규칙」 칸을 전부 보고 `gates.sh` 에 든다. 모델도
네트워크도 안 쓴다. 대장이 없거나 `candidates` 가 비면 「후보 0」으로 통과한다 — 아직 아무것도
판정하지 않은 상태다. 그 검사가 무는지는 CI 「게이트가 무는가」가 변조한 대장 열로 본다.

차이를 뽑는 쪽은 `scripts/compare-copies.py`, 그것이 무는지는 `scripts/test-compare-copies.py`
(임시 원본 · 원격 · 사본)와 CI 「게이트가 무는가」의 비교기 변조 다섯이 본다.

## 절차 지도와 설계 문서 (조각 2)

대장 둘과 달리 여기는 **문서의 모양**이다. 지금은 아무 스크립트도 읽지 않는다 — 다음 조각(로드맵 1,
리뷰 루프)이 설계 문서의 ② · ③ 을 읽게 되므로 그 제목을 여기서 못 박는다.

### 대상과 관계

| 대상 | 무엇 | 키 | 사는 곳 |
|---|---|---|---|
| **단계** | 한 조각이 지나는 자리 — 0 착수 전 · 1 기획 · 2 설계 · 3 구현 · 4 검증 · 5 배포 · 롤백 · 6 닫기 | 번호 | `docs/procedure.md` |
| **빈자리** | 단계 안에서 맡는 도구가 없는 자리 | 이름 | `docs/procedure.md` |
| **로드맵 항목** | 빈자리를 메우는 조각 | 순서 | `PRD.md` 의 조각 절 |
| **기획 문서** | 조각의 문제 · 시나리오 · 성공 기준 · 하지 않을 일 · 제약 | 조각 | `PRD.md` 의 절 |
| **설계 문서** | 아래 여섯 칸 | 조각 | `docs/design/<조각>.md` |
| **틀** | 위 둘을 새로 쓸 때 베끼는 것 | 종류 | `docs/templates/` |

```
단계 1 ── N 산출물 · 나가는 조건 · 맡는 도구
단계 1 ── 0..N 빈자리 1 ── 0..N 증거(PR) ── 0..1 로드맵 항목
조각 1 ── 1 기획 문서 ─┐
조각 1 ── 1 설계 문서 ─┴─ 한 PR ── 머지 뒤 ── N 구현 PR(⑥ 의 나눔)
```

### 설계 문서의 칸

여섯 다 **필수**다. 해당이 없으면 지우지 않고 `없음 — <이유>` 를 적는다 — 빈 칸과 안 본 칸을 가른다.
절 제목은 **아래 글자 그대로**다. 바꾸면 다음 조각의 리뷰 루프가 못 읽는다.

| 제목 | 담는 것 |
|---|---|
| `## ① 바뀌는 것` | 엔티티 · 계약 · 모듈 · 파일. 앵커볼트를 건드리면 그렇다고 |
| `## ② 보장하는 것 / 보장하지 않는 것` | 두 목록. 보장하지 않는 것은 **알려진 한계**다 — 리뷰가 이 밖을 짚으면 범위 밖이다 |
| `## ③ 받는 입력` | 이 변경이 읽는 입력의 모양. **검사 장치면 실제 파일에서 뽑은 닫힌 목록**이고 그 밖은 거절한다고 적는다 |
| `## ④ 결정` | 대안이 있던 결정과 ADR 번호. 한 가지밖에 없던 것은 사실이니 ① 에 |
| `## ⑤ 검증 계획` | 무엇으로 맞음을 보일지. 검사를 세우면 **어긋내 봐서 떨어지는 것**까지 |
| `## ⑥ PR 나눔` | 구현을 몇 PR 로, PR 마다 무엇을 닫는지 |

### 이 모양을 무는 것

**아직 없다.** 설계 문서에 여섯 제목이 다 있는지는 사람이 본다(`CHECKLIST.md`). 키 없이 볼 수 있는 검사이므로
자동화할 자리이고, 세우는 것은 로드맵이다 — 이 조각은 검사를 만들지 않는다(PRD 조각 2 하지 않을 일 1).
