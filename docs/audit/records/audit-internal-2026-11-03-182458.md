## 부적합 목록

### NC-36 · 원천이 있는 수 「two plugins」가 영어 수 낱말로, 닻 없이 적혔다 — 날짜 항목은 「원천이 있는 수는 둘 · 영어 수 낱말을 쓴 자리는 없다」고 적었다
- 규칙
  - ADR 0072 의 5(`docs/adr/0072-public-spread.md:30`): 「영어 README 에 적는 수는 아라비아 숫자로 쓰고 `verify-counts.py` 의 닻에 더한다」
  - 설계 ② E(`design.md:36`): 「`README.en.md` 가 원천이 있는 수를 아라비아 숫자로 쓰고, 그 수마다 `ANCHORS` 에 줄이 있다 — 원천은 지금 `SOURCES` 의 이름 그대로」
  - 설계 `:80`: 「영어 수 낱말을 쓰게 되면 그 자리는 아라비아 숫자로 고쳐 쓴다」
  - 성공 기준 6(`requirements.md:40`)
  - `verify-counts.py:216` 주석 · docstring `:33`(「수를 새로 적거나 … 이 목록을 함께 고친다」)
  - 날짜 항목 `design.md:111-113`: 「`README.en.md` 의 원천이 있는 수는 둘이다 … 영어 수 낱말을 쓴 자리는 없다」. 원천이 없다고 센 것으로 든 목록에도 이 수는 없습니다.
- 실제
  - `README.en.md:5` 「A Claude Code plugin marketplace with **two plugins**.」
  - 이 수에는 원천이 있습니다. `SOURCES` 「플러그인」(`verify-counts.py:170`, `*/.claude-plugin/plugin.json` — 지금 2: `vibe-audit` · `vibe-slice`)이고, 같은 원천을 `docs/architecture.md` 의 닻 「마켓플레이스와 플러그인 {N}.」(`:240`)이 이미 씁니다.
  - `ANCHORS` 의 `README.en.md` 줄은 「read-only auditors」 · 「document templates」 둘뿐입니다(`:217-218`).
  - L 은 영어 수 낱말을 읽지 못하고, U 의 명사는 한국어입니다. 그래서 지금 어느 검사도 이 자리를 보지 않습니다.
- 어느 쪽을 고칠 문제인가: 사람이 결정
  - (가) `README.en.md` 를 「2 plugins」로 쓰고 닻을 더한다
  - (나) 수를 빼고 원천을 가리킨다
  - (다) 원천이 있는 수가 아니라고 정해 날짜를 박은 새 항목에 까닭을 적는다
- 심각도: **보통**
  - 지금은 값이 맞습니다.
  - 그러나 ② E · 성공 기준 6 이 「원천이 있는 수는 다 물린다」고 믿게 하는 회귀를 막지 않습니다. 플러그인이 하나 늘면 밖 사람이 처음 읽는 입구가 말없이 「two plugins」로 남습니다.
  - 닫는 기록이 기준 6 을 글자대로 대면 미달입니다.
- 제안(고치지는 않음): 닫는 PR 에서 (가) ~ (다) 가운데 하나를 고르고, 날짜 항목의 「영어 수 낱말을 쓴 자리는 없다」를 날짜를 박은 새 항목으로 바로잡습니다. 「two trap cases」 · 「three or four」 · 「six cases」처럼 영어 수 낱말이 있는 자리를 「원천 없음」 목록에 다 들면 다음 사람이 같은 판단을 다시 하지 않습니다.

## 관찰

### OB-34 · 「세 회차 다 확인불가」의 원문이 README 가 가리키는 eval-log 에 없다
- 위치: `README.md:27-28` · `README.en.md:57-58` ↔ `docs/eval-log/2026-11.md:147`(run1 만 적음) ↔ `docs/audit/records/audit-quality-2026-11-03-075941.md:121`(회차 27 OB-1 — 「세 회차는 다 … 확인불가 U-1」)
- 무엇
  - 두 README 는 「표 · 판정 규칙 · 원문은 `docs/eval-log/2026-11.md` …」로 eval-log 를 가리킵니다.
  - 그 항목은 run1 의 확인불가만 적습니다. 셋 다라는 사실은 감사 기록과 압축본에만 있습니다.
- 왜 부적합이 아닌가
  - 사실은 원문과 맞습니다(회차 27 이 직접 읽었고, 회차 29 OB-29 가 run2 를 댔습니다).
  - ADR 0072 의 5 는 주인을 「`README.md` 와 eval-log」로 두었는데, `README.md` 가 그 문장을 듭니다.
  - 설계 ③ C 가 원문을 감사 기록의 자리로 정했습니다.
- 알아 둘 값: 밖 사람이 영어 README 의 가리킴을 따라가면 run1 하나만 봅니다. 닫는 기록이 성공 기준 4 를 댈 때 이 사실의 원문 자리를 함께 적으면 갈리지 않습니다(「문서에 없어서」 셋째).

### OB-35 · 영어 README 의 둘째 · 일곱째 절이 설계 ③ A 의 「옮기는 정도」와 갈린다
- 위치: `design.md:58-59`(③ A 6 · 7) ↔ `README.en.md:94-114` · `:116-124`
- 무엇
  - ③ A 7 은 「줄마다 (Korean)」인데, 구현은 절 제목에 한 번 달았습니다. 한국어 README 의 「작업 규칙」 줄(`CLAUDE.md` · `AGENTS.md`)을 빼고 `vibe-audit/README.md` 줄을 더했습니다.
  - ③ A 6 의 원천은 「호출 이름 · 「대략의 주기」」인데, 구현은 `vibe-audit/README.md` 의 「쓰는 법」(한 번에 하나 · 새 세션)과 「결과를 어떻게 다루나」(같은 감사자로 닫기), `audit-brief` 쓰는 법까지 옮겼습니다.
- 왜 부적합이 아닌가
  - `procedure.md:123` — 설계가 구현과 갈리는 것은 낡음이 아닙니다.
  - ② A · 성공 기준 2 가 요구하는 것은 절과 차례이고, 그것은 맞습니다.
  - 옮긴 문장은 원천과 뜻이 같습니다.
- 알아 둘 값: 닫는 기록이 기준 2 를 ③ A 에 댈 때 이 차이를 함께 적어야 「닫힌 목록」이 두 뜻으로 읽히지 않습니다.

### OB-36 · 판 받기 블록이 `vibe-audit` 하나만 든다
- 위치: `README.en.md:84-86` ↔ `README.md:69-72`(`claude plugin update <플러그인>@pdw96-kit`)
- 무엇
  - 한국어는 자리표시(`<플러그인>`)로 두 플러그인을 다 덮습니다. 영어는 `vibe-audit@pdw96-kit` 만 적었습니다.

- 왜 부적합이 아닌가: ② D 는 「판 받기 두 줄」만 요구하고, 그대로입니다. 원문보다 강한 문장이 아니라 좁은 문장입니다.
- 알아 둘 값: `vibe-slice` 를 깐 밖 사람은 그 플러그인의 새 판을 받는 줄을 영어에서 찾지 못합니다.

### OB-37 · 「You can call an auditor by name from an English session」에 잰 기록이 없다
