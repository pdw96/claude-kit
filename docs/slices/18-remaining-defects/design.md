**앵커볼트.** 건드리지 않는다 — 이름 · 감사자의 `tools` · 공통 절(`verify-copy.py` 의 `SHARED` 넷) · 대장의 모양 · 「…의 칸」 ·
`AGENTS.md`. 항목 10 과 끝 문단은 「체크 항목 뼈대」 · 「출력 형식」 뒤의 문단이라 공통 절이 아니다. `feedback.json` 은 칸과 상태 넷을
그대로 쓴다 — 바뀌는 것은 가른 FB 의 상태 · `feedback` · `reason` 끝의 꼬리뿐이다.

**고정 영역 · 수트.** `run-evals.sh` · `eval.yml` · 지난 정규식 그레이더 · 있는 v3 두 케이스(`gate-root-cause-auth` · `gate-comment-owned`)는
그대로다. 새 그레이더는 새 케이스의 것뿐이다. B 가 감사자 · 판을 고치면 route 지문(`eval-key.py route --list`)의 파일을 고친다 — 그 PR 의
CI 가 route 수트를 돈다. 케이스만 더하면 full 지문(`full --list`)만 바뀐다 — route 모드는 `route-*` 밖의 케이스 폴더를 빼므로(`eval-key.py`)
C · D 의 CI eval 잡은 지난 route 통과를 그대로 쓰고 다시 돌지 않는다. 그 PR 의 새 케이스가 지나간다는 근거는 CI 가 아니라 로컬 측정이다(⑤ C · D).
그 PR 의 FB 가 하나도 갈리지 않으면 `docs/eval-log/` 만 고쳐 수트가 돌지 않는다.

**사실.**
- FB-6 · 7 · 17 의 일반 몫과 FB-8 의 주석 · 독스트링 몫은 `c7cc318` 로 원본에 있다(호출 시 `audit-secrets` +292 · `audit-internal` +278,
  그 커밋 메시지). FB-8 의 「ADR 밖」 몫은 원본에 없다 — FB-34 가 그것이다(대장 FB-34 `reason`).
- 사본 레포는 원본의 새 항목 10 을 들지 않는다 — `compare-copies.py` 는 심을 때의 원본(`018842c`)과 견주므로 후보가 생기지 않고,

**시스템 구조.** 부품 · 경계 · 흐름은 그대로다. `docs/architecture.md` 는 고치지 않는다.

    새 쪽의 떨어짐이다 — 다시 재서 채우지 않는다. 둘 중 하나라도 못 미치면 그 판은 그 FB 에 **못 가름**이다.

## ⑤ 검증 계획

명령은 PR 본문에 결과와 함께 적는다. 「어긋내 보기」는 일부러 망가뜨린 작업트리에 같은 명령을 대어 떨어지는지 본 뒤 되돌린다.

**PR A**

- `./scripts/gates.sh` 스물넷 통과 — `verify-docs.py` 가 새 조각 폴더를, `verify-slice-gate.py` 가 착공 PR 에 결정 문서뿐인지를 본다(G2).
- 지문 — `git diff --name-only main...HEAD` 와 `eval-key.py route --list` · `full --list` 의 교집합 0.

**PR B** (A 가 머지된 뒤) — 커밋 순서가 측정의 순서다.

1. 케이스만 더한 커밋 — `verify-evals.py` · `verify-graders.py` 통과(K1). 옛 = 이 커밋의 원본 그대로다(③). `run-evals.sh --case <B 케이스>
   --ablation none --runs 3` → 목적 그레이더가 대조군이 지나간 회차 셋 중 둘 이상 떨어지는가(J2 옛 쪽). 못 미치면 둘째 판으로, 둘째 판도
   못 미치면 못 가름 — 케이스 · 문구 커밋을 내리고 eval-log 항목만 남긴다(K3 · W4).
2. 문구 커밋 — `audit-internal` · `budget.txt` · `plugin.json`. 같은 명령 → 세 회차 다 목적 그레이더와 대조군이 지나가는가(J2 새 쪽). `verify-budget.py` 통과 ·
   `budget.txt` diff(W2). `verify-copy.py vibe-audit/agents` 통과 · `git diff main...HEAD -- vibe-audit/agents` 가 W1 · W2 의 자리 안(W3).
3. 전수 — 2 의 머리에서 `workflow_dispatch` → verdict 초록(요구사항 성공 기준 6). `audit-internal` 의 판정 케이스(`gate-comment-owned` ·
   `trap-slice-scope`)가 이 안에서 문턱을 넘는다. PR 의 CI 는 route 수트 · gate · verdict 초록.
4. 기록 · 대장 — eval-log 항목 · README 표 · FB-34 · 8(L1). `verify-feedback.py` 통과. 이 커밋은 수트 지문 밖이다 — 전수를 다시 돌리지 않는다.

**PR C · D** (A 가 머지된 뒤, B 와 겹치지 않게 차례로) — 감사자는 고치지 않는다.

1. 케이스만 더한 커밋 — K1. 새 = 이 커밋의 원본, `--runs 3` → 세 회차 다 목적 그레이더와 대조군이 지나가는가. 옛 = 별도 worktree 에서
   ③ 의 그 FB 몫만 되돌린 판, 같은 명령 → 둘 이상 떨어지는가. C 는 FB-6 · FB-7 의 케이스를 따로 재고 따로 정한다(J4). 되돌린 diff 를
   PR 본문에.
2. 기록 · 대장 — eval-log 항목 · README 표 · L2. 못 가른 FB 의 케이스는 내리고 eval-log 항목만 남긴다 — 가른 FB 의 케이스는 그대로 둔다(K3 ·
   L3). 그 PR 의 FB 가 하나도 갈리지 않으면 eval-log 항목만 싣는다.
3. 감사자를 고치지 않으므로 전수를 돌리지 않는다 — 새 케이스가 `main` 에서 통과하는 근거는 1 의 새 쪽이다(요구사항 성공 기준 5).

**어긋내 보기** — 표본: 새 정규식 그레이더를 무르게 한 작업트리(예: 거짓 NC 를 찾는 정규식의 대상 낱말을 아무 낱말로)에 `verify-graders.py`
를 대면 그 그레이더를 지목한 표본에서 떨어진다. 측정 자체는 J2 의 옛 쪽이 어긋내 보기다 — 일반 몫을 뺀 감사자에 대어 떨어지는가.

**비용** — PR 마다 측정 비용을 PR 본문과 eval-log 에 적는다. 조각 합이 요구사항 「제약」의 $40 에 닿을 것 같으면 다음 측정 전에 멈추고 저자에게
올린다.

- `./scripts/gates.sh` 스물넷 통과 — 로컬과 CI gate 잡(요구사항 성공 기준 7).

**스스로 쓰기** — 각 PR 의 리뷰를 `slice-review` 로 가른다. PR 본문의 `## 리뷰 회차` 와 답글. B · C · D 는 `verify-slice-gate.py` 를
CI 에서 지나간다(이 착공이 머지된 뒤).

**단계 5(배포)** — B 가 가르면 플러그인 판이 오른다(0.4.1). 마켓플레이스로 설치한 레포는 `claude plugin marketplace update pdw96-kit` 뒤
`claude plugin update vibe-audit@pdw96-kit` 으로 받고 리로드한다(`README.md` · ADR 0013). 사본 레포는 다음 심기에서 받는다(하지 않을 일 5).
C · D 는 배포처가 없다 — 수트에 케이스가 늘 뿐이다. 되돌리는 길은 그 PR 의 되돌림이다 — 대장의 FB 는 되돌림과 함께 `defect` 로 돌아간다.
