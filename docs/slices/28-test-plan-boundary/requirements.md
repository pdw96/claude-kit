# 조각 28 — 착공 시험 계획의 경계 (2026-10-19 착공)

요구사항이다 — **무엇을 · 왜.** 어떻게 · 경계는 같은 폴더의 `design.md`, 대안이 있던 결정은 ADR 0039.

이 조각을 「다음 조각」으로 적은 것은 조각 27 의 `## 닫으며 (2026-10-19)` 다 — 그 기록의 「넘긴 것」(없음) · 「지켜본 것」 다섯을 읽고 착공한다
(ADR 0012). 「다음 조각」 문단이 이 줄을 순서 28 로 매기며 `docs/procedure.md` 「설계 문서의 칸」 ⑤ 와 스킬 `slice-review` 에 어떻게 넣을지를 이
조각에 넘겼다 — ADR 0039 가 정한다. 「지켜본 것」 다섯 가운데 넷(`--merge` 의 첫 실물 · 대장의 `agents_path` 꼴 · `bite-gates.sh` 의 시간 · 조각 26
의 수트 셋)은 이 조각이 다루지 않는다(하지 않을 일 7). 「얕은 클론」은 이 착공 세션의 클론이 얕지 않았다(`git rev-parse --is-shallow-repository` →
`false`).

## 문제

**착공 설계가 시험을 어디까지 드는지 절차가 말하지 않는다.** `docs/procedure.md` 「설계 문서의 칸」 ⑤ 는 「무엇으로 맞음을 보일지. 검사를 세우면
어긋내 봐서 떨어지는 것까지」뿐이다. 착공이 시험의 꼴 하나하나까지 닫아야 하는지, 그 빈칸을 짚은 리뷰가 안인지 밖인지를 `slice-review` 가 가를
기준이 없다.

- **착공 PR #101 — 리뷰 다섯 회차, 지적 스물하나.** 조각 「`sync-agents.sh --merge`」의 착공 설계 ② 「시험」이 꼴(T1 ~ T13)과 변조본의 대응표를 들었다.
  지적은 5 → 6 → 3 → 4 → 3 이었고 6회차에 0 이었다(3라운드 한도를 넘어 저자가 4 · 5 · 6회차를 다시 불렀다). 이 착공 세션이 스물하나를 그 PR 의
  답글과 고친 커밋으로 다시 갈랐다(2026-10-19) — 지적마다의 갈래는 설계 ③.

  | 회차 | 지적 | 규칙의 빈칸 | 꼴의 빈칸 | 그 밖 |
  |---|---|---|---|---|
  | 1 | 5 | 0 | 1 | 4 |
  | 2 | 6 | 4 | 2 | 0 |
  | 3 | 3 | 0 | 3 | 0 |
  | 4 | 4 | 0 | 3 | 1 |
  | 5 | 3 | 0 | 1 | 2 |
  | 합 | 21 | 4 | 10 | 7 |

  **규칙의 빈칸**은 한 갈래의 시험이 다 같이 보지 않는 것이다 — 거절 시험이 종료 코드를 보지 않음 · 성공 시험이 대장 전체와 파일별 표를 보지 않음 ·
  변조본이 없는 시험. **꼴의 빈칸**은 보장의 한 조건에 그것을 어기면 떨어지는 꼴이 없는 것이다 — 원본에서 파일을 뺀 꼴 · 받기만 실패하는 원격 ·
  원격보다 앞선 사본 같은. **그 밖**은 보장 자체의 빈칸과 사실의 틀림이다(그 가운데 하나는 대응표의 변조본이 rc 255 를 흘리지 못한다는 틀림이다).
- **규칙의 빈칸은 한 번에 닫혔고 꼴의 빈칸은 닫히지 않았다.** 규칙의 빈칸 넷은 다 2회차에 나왔고, 그 회차에 쏠림 신호가 서 저자가 「규칙으로 전수」로
  정한 뒤(V1 ~ V4) 다시 나오지 않았다. 꼴의 빈칸은 회차마다 1 · 2 · 3 · 3 · 1 이었다 — 규칙을 세운 뒤의 3 ~ 5회차에도 일곱. 코드가 없는 자리에서
  보장 열넷(P1 ~ P6 · M1 ~ M8)의 조건과 거절 · 성공 길의 조합을 다 적으려 하니, 리뷰가 회차마다 빠진 조합을 몇 개씩 찾았다.
- **그 조각은 자기 몫만 정했다** — ADR 0038 의 12(착공은 보장 목록과 시험 규칙까지, 꼴의 목록은 구현 PR 이 코드와 함께) · 13(이유 코드로 갈래와 시험의
  대응을 게이트가 문다). 그 뒤 구현 PR #102 의 리뷰는 두 회차(3 · 0)였고 꼴의 빈칸은 없었다 — 1회차 셋은 임시 폴더의 자리 · 시험 고정물의 크기 ·
  병합 도구의 커밋 안 된 변경이었다(조각 27 「닫으며」 「리뷰가 찾은 갈래」).
- **다른 검사 조각은 꼴을 들고도 짧았다** — 조각 「main 푸시가 통과한 수트 지문을 읽게」의 착공 #52 는 시험 T1 의 꼴 열둘을 착공에서 들고 Codex 한
  회차(지적 0)였다. 그 꼴은 ③ 받는 입력의 닫힌 목록(워크플로와 API 응답에서 뽑은 것) 하나하나였다 — 규칙이 「③ 의 꼴마다 하나」면 꼴은 ③ 이 이미
  닫는다. #101 의 꼴은 ③ 이 아니라 보장의 조건에서 나왔다.
- **다음 검사 · 스크립트 조각도 같은 회차를 부른다.** ADR 0038 은 그 조각의 기록이라 다음 조각의 착공 설계와 그 리뷰를 가르는 기준이 되지 않는다.
  같은 틀과 스킬을 받는 다른 레포(`vibe-slice` 플러그인 · 사본)도 같다.

## 핵심 사용자와 시나리오

- 사용자: 검사 · 스크립트 조각을 착공하는 세션과 그 저자. 이 저장소와 `vibe-slice` 를 받은 다른 레포가 같다.
- 시나리오: 세션이 스킬 `slice-docs` 로 착공한다 → 설계 ⑤ 에 보장의 조건마다 무엇으로 보일지와 시험 규칙(거절 시험이 보는 것 · 성공 시험이 보는 것 ·
  조건마다 꼴 하나 이상 · 시험마다 변조본)을 적고, 꼴 하나하나는 적지 않는다 → 리뷰 봇이 「P3 의 줄이 둘인 꼴이 없다」를 짚는다 → 세션이
  `slice-review` 로 **밖**(⑤ 가 구현 PR 에 맡긴 꼴)이라 답글하고 그 구현 PR 을 가리킨다. 「거절 시험이 종료 코드를 보지 않는다」는 **안**이라 ⑤ 의 규칙을
  고친다 → 착공이 머지된다 → 구현 PR 이 꼴을 시험 코드로 들고, 보장의 조건 → 꼴 → 변조본 대응을 PR 본문에 싣는다 → 그 PR 의 리뷰가 꼴의 빈칸을
  짚으면 `slice-review` 가 ⑤ 의 규칙(조건마다 꼴 하나 이상)에 비춰 **안**으로 가르고 고친다.

## 성공 기준

1. **절차가 경계를 든다** — `docs/procedure.md` 「설계 문서의 칸」 ⑤ 행의 「담는 것」이 든다: 시험을 세우는 조각의 착공은 보장의 조건마다 무엇으로
   보일지와 시험 규칙까지 들고, 꼴 하나하나는 구현 PR 이 시험 코드로 들며 보장의 조건 → 꼴 → 변조본 대응은 그 PR 본문이 든다. 규칙과 꼴을 가르는 말(한
   갈래의 시험이 다 지는 것 / 한 조건의 시험)과 ③ 이 닫힌 목록일 때(규칙이 그 목록을 가리킨다)도 든다. 틀 `design.md` ⑤ 의 안내가 같은 말이다. 「…의
   칸」 네 절의 제목과 표 서식은 바이트가 그대로다 — `verify-docs.py` 가 지나간다.
2. **`slice-review` 가 가른다** — 「2. 가르기」 밖 갈래에 「착공 PR 에 ⑤ 가 구현 PR 에 맡긴 꼴을 채우라는 요구」가 들고, 「1. 기준」 구현 PR 줄의 그 줄이
   닫는 몫에 「⑤ 의 규칙」이 든다.
3. **#101 에 대면 갈린다** — 설계 ③ 의 지적 스물하나를 B 의 `slice-review` 로 다시 가르면 꼴의 빈칸 열이 **밖**(구현 PR 이 받는다)이고 규칙의 빈칸
   넷과 그 밖 일곱, 열하나가 **안**이다 — 지금 갈래(스물하나 다 안)와 다르다. #102 의 지적 셋은 갈래가 그대로다 — 안 둘 · 말하지 않음 → 보장 하나(설계 ③). 지적마다의 갈래 표를 B 의 PR
   본문에 싣는다.
4. **판과 지도가 맞다** — `vibe-slice` 판이 0.4.3 이고, 두 스킬의 지도 링크가 B 의 지도를 박는다 — `verify-map-pin.py` 가 지나간다.
5. **예산 천장 안이다** — `slice-review` 호출 시 문자가 천장 4,500 이하이고(ADR 0004 — 천장은 그대로), `vibe-audit/evals/budget.txt` 가 새 값이다.
6. **사례가 있다** — `docs/procedure.md` 「사례」에 claude-kit #101 절이 있다 — 회차마다 규칙 · 꼴 · 그 밖, #102 의 회차, 반대 사례 #52, 이유 코드는 그
   조각의 장치라는 것.
7. `./scripts/gates.sh` 가 이 조각의 PR 마다 로컬과 CI gate 잡에서 통과하고, 검사 수는 스물넷 그대로다. 이 조각의 PR 은 수트 지문(`eval-key.py route
   --list` · `full --list`) 밖이다 — eval 잡이 건너뛴다.

## 하지 않을 일

1. **지난 기록을 고치지 않는다** — 조각 27 의 설계 · ADR 0038 의 12 · 13 은 그대로다. 지난 조각들의 ⑤ 를 새 규칙으로 다시 가르지 않는다.
2. **이유 코드를 절차에 일반화하지 않는다** — 「사례」에 그 조각의 장치로 적기만 한다(ADR 0039 의 5).
3. **⑤ 의 내용을 키 없이 물지 않는다** — 새 검사를 세우지 않는다. `verify-docs.py` 는 제목만 본다(ADR 0010). 규칙이 있는지 · 꼴이 빠졌는지는 뜻이라
   리뷰가 본다.
4. **「…의 칸」의 제목 · 표 서식과 ⑤ 밖의 칸을 바꾸지 않는다** — 앵커볼트(`CLAUDE.md`). ② · ③ 행 · 요구사항 · 의도 · 마스터플랜의 칸은 그대로다.
5. **사본 레포를 다시 심지 않는다** — ERP 의 스킬 사본은 그 레포가 다음에 `sync-slice.sh` 로 심을 때 바뀐다(`INTENT.md` Not 4).
6. **예산 천장을 올리지 않는다** — `slice-review` 의 여유 57 자 안에서 쓴다(ADR 0004).
7. **조각 나눔의 다른 줄과 조각 27 「지켜본 것」을 다루지 않는다** — 「회수율 측정」 · 「가르지 못한 결함 다섯」 · 「항목 10 과 머리의 어긋남」 ·
   「가르지 못한 빈 갈래 둘」.
8. **쏠림 신호 · 리뷰 한도 · 답글 · 회차 표의 규칙을 바꾸지 않는다** — `slice-review` 의 3 ~ 7 은 그대로다.

## 제약

- 스택: 문서와 스킬 문구뿐이다 — 코드를 고치지 않는다. 판 · 예산 · 지도 판의 검사(`verify-manifest.py` · `verify-budget.py` · `verify-map-pin.py`)는 그대로
  쓴다.
- 원본: `main` `5ac0dd2`. `docs/procedure.md` 는 `e8314cc`(조각 9 닫기)에서, `vibe-slice/` 는 `d561c67`(조각 10 PR C)에서 마지막으로 바뀌었다. 두 스킬의
  지도 링크는 `fe31909` 를 박았다 — 그 뒤 지도가 바뀌지 않아 `verify-map-pin.py` 가 지나간다.
- 예산: `slice-review` 호출 시 4,443 / 천장 4,500 — 여유 57 자.
- 지도 판: 지도와 플러그인을 한 PR 에서 고치므로 커밋이 둘 든다 — 지도를 고친 커밋, 그 커밋을 박은 커밋(ADR 0019 결과 2 · 7).
- CI: `docs/` · `vibe-slice/` · `vibe-audit/evals/budget.txt` 는 두 수트 지문 밖이다 — eval 잡이 건너뛴다.
- 비용: 모델 호출이 없다.
- 기간: 구현 PR 하나까지 **이틀**(2026-10-21 까지).
- 리뷰: PR 본문에 설계 ② 를 적고, 착공 PR 도 구현 PR 도 스킬 `slice-review` 로 가른다. PR 마다 **3라운드**를 넘기면 소유자가 판정한다.

## 닫으며 (2026-10-19)

변조본의 대응은 그 PR 본문으로 든다(ADR 0039). 코드 · 스크립트 · `gates.sh` · 사본 레포는 그대로다. 넘긴 것은 없다.

### 배포

#105 의 머지가 배포다(설계 ⑤ 「단계 5」) — `vibe-slice` 0.4.3 이 장터에 섰다. 보이는 것은 `main` 의 `plugin.json` 판 `0.4.3` 과
