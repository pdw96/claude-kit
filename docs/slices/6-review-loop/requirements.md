# 조각 6 — 리뷰 루프 (2026-10-07 착공)

요구사항이다 — **무엇을 · 왜.** 어떻게 · 경계는 같은 폴더의 `design.md`, 대안이 있던 결정은 ADR 0014.

## 문제

리뷰 회차가 끝나지 않는다(`INTENT.md` Why). 조각 2 는 그 까닭을 둘로 봤다 — 설계에 ② · ③ 칸이 없었고, 지적을 설계에
비춰 가르는 자리가 없었다(조각 2 요구사항 「문제」). 칸은 조각 2 가 세웠고 문서 대조 검사가 문다. 남은 것은 가르는 자리다.
절차 지도는 그것을 빈자리 「변경 관리」로 두고 한 문단(「4 에서 지적은 설계에 비춰 가른다」)만 적었다.

**claude-kit 은 그 문단대로 손으로 갈랐는데도 회차가 줄지 않았다.** PR #14 ~ #27 의 Codex 리뷰를 다시 셌다(2026-10-07).

- **「범위 밖」은 거의 나오지 않았다.** 지금 문단은 지적을 둘로 가른다 — ② 의 보장을 어기면 안, 보장하지 않는 것을 짚으면
  밖. 설계가 **말하지 않은** 경계는 어느 쪽인지 정하는 규칙이 없어 다 「안」이 되어 고쳐졌고, 리뷰가 회차마다 그 칸을 한
  자리씩 채웠다. 조각 2 「닫으며」 · 조각 4 「닫으며」가 같은 꼴을 적었다.
- **착공 PR 은 비춰 볼 설계가 없다.** 착공 PR 은 설계 자체가 리뷰 대상이라 ② 가 기준이 될 수 없다. 회차가 가장 긴 PR 셋이
  착공 PR 이다.
- **같은 갈래가 회차를 나눠 나왔다.** #24 의 마켓플레이스 갱신 경로는 1 회차(리로드)와 2 회차(install 전 갱신)에 나뉘어
  나왔고, #20 의 ⑤ 지적 열다섯은 여섯 회차에 흩어졌다. 강호쟁패 `CLAUDE.md` 의 「지적 하나를 고칠 때는 같은 종류를 모두
  찾는다」(PR #1 의 줄바꿈 세 번)와 ERP `docs/리뷰-루프.md` 의 「쏠림 신호」(ERP#18)가 같은 것을 다른 레포에서 따로 배웠다.
- **다른 레포는 가르는 법을 스스로 세웠다.** ERP 는 점수 · 문턱 · 방안 A ~ E 를, 강호쟁패는 P0 ~ P2 병합 기준(ADR-0005)을
  둔다. 둘 다 그 레포의 문서에 있고 설계 ② · ③ 에 기대지 않는다 — 강호쟁패에는 틀이 가기 전까지 설계 문서가 없었다.

## 핵심 사용자와 시나리오

- 사용자: 저자 한 명, 그리고 PR 을 모는 Claude Code 세션(이 레포와 틀대로 선 다른 레포).
- 시나리오: 구현 PR 에 Codex 리뷰가 온다 → 세션이 스킬 `slice-review` 를 부른다 → 스킬이 PR 이 어느 조각의 어느 PR 인지 정하고
  (착공 · 구현 · 닫는 PR) 그 PR 의 기준을 읽는다 — 구현 PR 이면 그 조각 설계 ② · ③ 과 설계 끝의 날짜 항목 → 지적의 사실을
  리뷰한 커밋에서 확인해, 재현되지 않으면 **반박됨**(확인한 시도를 들어 답글)으로 두고, 재현되면 **안**(고친다) · **밖**(근거
  줄을 들어 답글) · **말하지 않음** 으로 가른다 → 말하지 않음은 바로 고치지 않고 같은 갈래를 그
  자리에서 전수로 찾은 뒤 경계를 정해 설계 끝에 날짜 항목으로 박고, 그 결과대로 갈래째 고치거나 답글로 넘긴다 → PR 본문의
  회차 표에 그 회차를 적는다 → 같은 변경 단위를 두 회차 연속 짚어 쏠림 신호가 서면(조건은 설계 S4 — ERP 의 조건 그대로)
  고치기를 멈추고 회차 표를 들고 저자에게 묻는다 → 요구사항 「제약」의 리뷰 한도를 넘으면 저자가 판정한다 → 조각을 닫을 때 「닫으며」가 그 회차 표를 센다.
  강호쟁패는 `vibe-slice` 갱신으로, ERP 는 `sync-slice.sh` 로 같은 스킬을 받는다.

## 성공 기준

1. 마켓플레이스의 `vibe-slice` 에 스킬이 둘(`slice-docs` · `slice-review`)이고 판이 오른다. `claude plugin validate ./vibe-slice` ·
   `verify-manifest.py` 가 통과하고, `verify-budget.py` 가 `slice-review` 를 잰다 — 상시 ≤ 900, 호출 시 ≤ 4,500.
2. `sync-slice.sh` 를 임시 git 레포에 돌리면 `.claude/skills/` 에 `slice-docs` · `slice-review` 둘이 서고, 각 `SKILL.md`
   프론트매터 뒤에 출처 커밋이 박힌다. 둘 가운데 하나라도 폴더로 있으면 `--force` 없이 아무것도 쓰지 않고 멈춘다.
   `test-sync-slice.py` 가 이것과 조각 5 의 C2 · C4 · C5 를 문다.
3. 갈래 재연 — 세션이 스킬을 claude-kit 의 지난 지적 30 건(착공 #17 13 · #24 12, 구현 #18 5)에 대어, 지적마다 갈래와 근거 줄
   (기준 문서의 줄, 또는 「말하지 않음 — <비어 있는 경계>」) — 재현되지 않으면 반박됨과 확인한 시도 — 을 내고, 말하지 않음은 같은 갈래끼리 묶어 갈래 수를 지적 수와 함께
   적는다. 그 표가 구현 PR 본문에 있고 저자가 본다.
4. 이 조각의 구현 PR 리뷰를 스킬로 가른다 — PR 본문에 회차 표가 있고, 지적마다 답글에 갈래와 근거 줄(반박됨이면 확인한
   커밋과 시도)이 있으며, 말하지 않음으로 정한 경계는 설계 끝의 날짜 항목에 있다.
5. 규칙이 한 군데다 — 세 갈래 · 기준 · 쏠림 신호 · 회차 표의 규칙은 `slice-review` 의 스킬 폴더에만 있고(갈래의 정의는
   `SKILL.md`, 회차 표 · 답글의 꼴은 `SKILL.md` 나 그 옆 파일 — 설계 S7), `docs/procedure.md`
   의 단계 4 와 `CHECKLIST.md` 는 그 스킬을 가리킨다(grep 으로 「말하지 않음」 정의가 한 파일에서만 나온다).
6. 강호쟁패(플러그인)와 ERP(사본)의 세션에서 `slice-review` 가 뜬다 — 저자가 단계 5 에서 본다.
7. `./scripts/gates.sh` 가 구현 PR 마다 통과하고, 구현 PR 이 바꾼 파일 가운데 수트 지문(`eval-key.py route --list` ·
   `full --list`)에 드는 것이 0 이다 — 이 조각의 파일로는 route 수트가 돌지 않는다.

## 하지 않을 일

1. **리뷰어 쪽을 고치지 않는다** — 리뷰 봇의 설정과 `AGENTS.md` 「Review guidelines」(고정 영역)는 그대로다. 리뷰어가 무엇을
   짚는지가 아니라 짚은 것을 어떻게 가르는지만 다룬다.
2. **ERP 의 점수 · 문턱 · 방안 A ~ E 를 일반형으로 올리지 않는다** — 멈춤은 쏠림 신호 하나다(ADR 0014 의 3). ERP 의
   `docs/리뷰-루프.md` 와 강호쟁패의 병합 기준은 그 레포의 것으로 남는다.
3. **지적의 분류를 검사로 물지 않는다** — PR 본문 · 리뷰 스레드는 저장소 밖이라 `gates.sh` 가 볼 수 없다. 회차 표는 사람이
   본다(`CHECKLIST.md`).
4. **스킬이 머지하거나 리뷰를 다시 부르는 때를 정하지 않는다** — 머지는 저자가 하고, 리뷰를 부르는 법은 레포마다 다르다
   (ERP 의 draft 해제 · `@codex review`).
5. **리뷰 한도의 숫자를 정하지 않는다** — 조각마다 요구사항 「제약」이 든다.
6. **「…의 칸」 네 절과 틀의 `##` 제목을 바꾸지 않는다** — 설계 ② · ③ 의 칸은 그대로 두고, 말하지 않음의 결과는 설계 끝의
   날짜 항목(이미 있는 덧붙이는 자리)에 쓴다.
7. **강호쟁패 · ERP 저장소를 이 조각의 PR 에서 고치지 않는다** — 플러그인 갱신과 사본 심기는 저자가 단계 5 에서 한다.
8. **스킬의 트리거 수트를 세우지 않는다** — 조각 5 와 같다. 부를 수 있는지는 단계 5 에서 저자가 본다.

## 제약

- 스택: bash · python3 표준 라이브러리, 마크다운. 스킬의 모양은 `claude plugin validate` 가 받는 것.
- 모델 비용: 이 조각의 파일로는 route 수트가 돌지 않는다 — `vibe-audit/` · `eval.yml` 을 건드리지 않는다. 다만 CI 의 CLI 판이
  오르면 판마다 한 번 돈다 — 판이 수트 지문에 들고(`eval-key.py`), CI 는 판을 고정하지 않는다(`CLAUDE.md` 「스택」). 착공 PR
  #28 의 머리 399acb9 에서 그렇게 한 번 돌았다(2.1.292 → 2.1.293). 갈래 재연(성공 기준 3)은 세션 한 번이다.
- 글자 예산: `slice-review` 의 상시 ≤ 900 · 호출 시 ≤ 4,500, `vibe-slice` 상시 합계 ≤ 5,600(ADR 0013 의 8). 천장은 올리지 않는다.
- 기간 **이틀**.
- `./scripts/gates.sh` 는 지금 열넷이 그대로 통과해야 한다.
- 리뷰: PR 본문에 설계 ② 를 적는다. 착공 PR 은 지금 문단대로 가르고, 구현 PR 은 스킬 `slice-review` 로 가른다. **3라운드**를
  넘기면 소유자가 판정한다.

### 제약에서 어긋난 것

- **리뷰가 3라운드를 넘었다 — #28, 소유자가 판정했다.** Codex 일곱 회차(지적 5 → 5 → 7 → 7 → 1 → 2 → 3, 4 ~ 7 회차를
  소유자가 불렀다). 8 회차 없이 머지했고 머지할 머리 0794ab2 는 리뷰되지 않았다. #29 는 두 회차, #30 은 세 회차로 한도 안이었다.
- **`vibe-audit/` 를 건드렸다.** 「이 조각의 파일로는 route 수트가 돌지 않는다 — `vibe-audit/` · `eval.yml` 을 건드리지
  않는다」인데, 예산 스냅숏 `vibe-audit/evals/budget.txt` 를 #29 · #30 에서 고쳤다(스킬을 재면 쓰는 자리다). 그 파일은 수트
  지문 밖이라 route 는 돌지 않았다 — 제약의 뜻(모델 비용)은 지켰고 글자는 어겼다. 착공 때 예산 스냅숏의 자리를 보지 않았다.
- route 수트는 #28 의 머리 399acb9 에서 CLI 판 올림(2.1.292 → 2.1.293)으로 한 번 돌았다 — 제약에 적어 둔 대로다.
- 기간은 이틀 안이었다(2026-10-07 착공, 2026-10-08 닫음).

### 리뷰가 찾은 갈래

- **#28 — 고침이 다음 회차의 지적을 낳았다.** 일곱 회차 지적 30 건의 여럿이 앞 회차의 고침이 들인 자리였다 — 이 조각이 풀려던
  수렴하지 않는 회차가 착공 PR 에서 그대로 재현됐다. 3 회차부터 소유자가 회차마다 판정했고, 4 회차에 「아직 겪지 않은
  가설적 경계 사례」를 보장하지 않는 것에 넣어 경계를 채우는 길을 끊었다. 그 뒤 회차의 지적은 1 · 2 · 3 으로 줄었다.
- **갈래 재연 — 스킬은 「안」인 같은 종류가 회차를 나눠 다시 오는 것을 막지 못한다.** 18-3 → 18-5(되부름), 24-1 → 24-8 ·
  24-9(갱신 경로). 스킬은 전수를 말하지 않음에만 요구한다. 저자가 스킬을 넓히지 않고 한계로 두었다(2026-10-08). 실제로는 이
  조각의 세션이 안에도 전수를 대어 봤고, #29 1 회차에서 둘, #30 2 회차에서 하나를 더 찾아 같은 커밋에 고쳤다 — 그래도 #30 은
  1 회차(옮기며 경우가 빠짐)와 2 회차(새 규칙이 답글 꼴에 덜 건너감)가 가까운 종류로 이어졌다.
- **#29 · #30 — 설계 ② 를 스킬로 줄이며 규칙이 빠졌다.** 구현 PR 지적 다섯이 모두 이 갈래다 — 겹친 지적의 셈 · 닫는 PR 의
  대체 기준(#29 1 회차), 사라진 커밋(#30 1 회차), 넘긴 보장 · 기대는 자리의 근거(#30 2 회차). 전수로 더 찾은 셋도 같다 — 몫의
  셈 · 기존 결함을 넘기는 곳(#29), 밖의 처리에 ⑥ 의 다른 줄(#30). 3,963 자의 설계 ② 를 3,159 자로 줄일 때 문장을 하나씩 대어
  보지 않았다. 교훈 — 설계를 스킬로 줄일 때는 설계 ② 의 문장마다 스킬의 자리를 짝지어 보고, 고친 규칙은 그 규칙을
  읽는 다른 절(답글 꼴 · 회차 표)까지 따라간다.
- **단계 5 — 사본이 원본의 결함을 먼저 찾았다.** ERP 가 사본을 다시 심은 PR(pdw96/ERP#102)의 리뷰가 사본을 넷 고쳤고, 넷 다
  「다른 레포에서도 같은 말」이라 원본으로 옮겼다(#30, ADR 0015). 같은 날 저자가 ERP 쪽 규칙을 정했다 — ERP 가 겪지 않는
  조각 상황을 짚은 사본 지적은 ERP 에서 고치지 않고 원본으로 넘긴다(pdw96/ERP#103).
- **단계 5 — 받은 두 레포 모두 조각 문서가 없다.** `slice-review` 는 지금 claude-kit 안에서만 가를 수 있다. 성공 기준 6 은
  「뜬다」까지라 실패가 아니고, 설계의 「설계 문서가 없는 레포」 한계 그대로다. 다른 레포에서 쓸모가 생기려면 그 레포가 조각
  방식(`slice-docs`)을 들여야 하고, 그것은 각 레포의 결정이다 — 조각 나눔에 줄을 더하지 않는다(저자, 2026-10-08).

### 넘긴 것

- 넘긴 성공 기준은 없다.
- **사본 머리줄** — 조각 나눔에 줄을 더했다. `sync-slice.sh` 가 다시 심을 때마다 그 레포가 고정한 절차 지도 링크를 지우고,
  머리줄의 「원본으로 되먹이지 않는다」가 원본으로 넘기는 길(#30 · ADR 0015)과 어긋나게 읽힌다. 같은 자리라 한 줄이다.
