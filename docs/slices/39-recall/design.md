## ② 보장하는 것 / 보장하지 않는 것

**보장하는 것**

- E **러너의 폴더.** `run-evals.sh` 가 `--eval-dir <폴더>` 를 ③ A 의 닫힌 목록으로 받는다.
  - E1 없으면 지금 그대로 — 하네스의 기본 `evals/` 이고, 결과 정리도 `vibe-audit/evals` 를 본다.
  - E2 `recall` 이면 하네스에 같은 깃발을 넘기고, 돌기 전의 두 검사 · 결과 폴더 · 결과 정리(고른 케이스 전부 · 회차 수 · 모델 확인 · 실패 회차의 트레이스)가
    `vibe-audit/recall` 을 본다. 지금의 결과 정리가 문 것은 회수율 폴더에서도 똑같이 문다.
  - E3 그 밖의 값이면 하네스를 부르기 전에 종료 2.
- N **회수율 줄.** E2 의 실행이 끝에 케이스마다 `회수 <케이스> <찾은 회차>/<회차>` 와 합 `회수율 <찾은 회차 합>/<회차 합>` 을 찍는다. 「찾았다」는 그 회차에서 목적
  그레이더(② M2)가 통과한 것이다. 이 줄은 종료코드를 바꾸지 않는다 — 문턱이 없다(ADR 0050 의 2). 종료는 하네스와 지금의 결과 정리의 것이다.
- G **수트와 갈림.** 인자 없는 `run-evals.sh` 와 `--case 'route-*'` 는 하네스의 기본 폴더만 돌아 회수율 케이스를 돌리지 않는다. `eval.yml` 은 그대로다.
- K **지문.** `eval-key.py` 의 두 모드(route · full)가 `vibe-audit/recall/` 아래 파일을 넣지 않는다 — 회수율 케이스만 고친 PR 은 route 수트를 돌리지 않는다.
  러너는 두 모드에 그대로 든다.
- M **회수율 케이스의 모양.** `verify-evals.py` 가 인자 없이 `vibe-audit/evals` 와 `vibe-audit/recall` 을 다 본다(폴더가 없으면 회수율 쪽은 0 케이스로 지나간다).
  인자로 폴더 하나를 주면 그 폴더 하나다 — 이름이 `recall` 이면 회수율 규칙으로 본다. `evals` 의 규칙은 그대로다. 회수율 케이스마다:
  - M1 이름이 `recall-` 로 시작하고, `prompt.md` 가 감사자 하나를 이름으로 지목한다(판정 케이스와 같은 법).
  - M2 목적 그레이더가 꼭 하나다 — `recall-found`, `type: regex`, `target: last_message`. NC 절 안에서 결함의 자리(파일)와 결함의 흔적이 함께 나와야 한다
    (`real-nc-found` 와 같은 모양 — `vibe-audit/evals/README.md` 「그레이더와 대조군」).
  - M3 `auditor-fired` 가 `subagent_type` 에 걸리고 `arm: with-only` 다(판정 케이스와 같은 규칙).
  - M4 그 밖의 그레이더는 없다 — 대조군 `real-nc-found` 를 두지 않는다. 심은 결함이 곧 실제 결함이라, 아무것도 내지 않는 감사자는 M2 에서 떨어진다(ADR 0050 의 7).
  - M5 `case.yaml` 의 `description` 이 `출처:` 줄을 든다 — 대장의 자리 · 담당 감사자가 감사한 커밋 · 찾은 쪽(③ B).
  - M6 `verify-graders.py` 가 인자 없이 두 폴더를 보고, 회수율 케이스는 표본이 **필수**다 — `samples/pass.md` 하나 이상과 `samples/fail*.md` 하나 이상(③ D).
    판정 케이스의 표본 규칙은 그대로다(선택).
- V **문다.** `bite-gates.sh` 의 두 검사 절이 회수율 케이스의 변조본을 떨어뜨리고, 진짜 수트(두 폴더)는 지나간다 — ⑤ 의 시험 규칙.

**보장하지 않는 것(알려진 한계)**

- **정밀도** — 회수율 케이스는 엉뚱한 NC 를 함께 내도 떨어지지 않는다. 다 걸고 보는 감사자는 회수율이 높다. 그것은 오검 쪽 케이스가 잰다(요구사항 하지 않을 일 3).
- **원래보다 쉬운 픽스처** — 몇 파일짜리 픽스처는 ERP 의 수천 줄보다 볼 것이 적다. 회수율은 높게 나올 쪽으로 기운다. 기준선은 같은 픽스처끼리 견주는 자로만
  쓴다 — ERP 에서의 회수율이 아니다.
- **흔들림** — 케이스마다 세 회차다. 한 회차 차이는 판정이 아니다(`vibe-audit/evals/README.md` 「러너」의 `runs: 3`).
- **수트 모델 밖** — 감사자는 `model: inherit` 라 사용자 세션의 모델로 돈다. 기준선은 러너가 박은 수트 모델의 숫자다.
- **놓친 증거가 없는 감사자** — `audit-secrets` · `audit-ops` · `audit-quality` · `audit-internal` 은 케이스가 없다(요구사항 하지 않을 일 6).
- **익명화의 빈틈** — ③ C 의 낱말 목록 밖에서 사본을 알아보게 하는 것(코드의 모양 · 주석의 말투)은 사람이 본다(`CHECKLIST.md` 「되먹임이라면」의 첫 줄과
  같은 눈).
- **정규식의 한계** — `recall-found` 는 「같은 NC 절 안에 함께 있음」으로 짐작한다(`vibe-audit/evals/README.md` 「정규식 그레이더」의 한계 표 그대로).

## ④ 결정

**정한 것**

- 재료는 담당 감사자가 놓친 결함이다 — 감사자가 찾은 결함이나 둘을 반씩 대신. ADR 0050 의 1.
- 회수율 케이스는 전수 verdict 의 문턱 밖에서 재기만 한다 — 문턱에 넣는 것 대신. ADR 0050 의 2.
- 케이스는 여섯 · 로컬 측정은 조각 전체 $30 안이다 — 셋 · $15 나 열 · $50 대신. ADR 0050 의 3.
- 자리는 `vibe-audit/recall/` 이고 러너가 `--eval-dir` 로 받는다 — `evals/` 안의 접두 · `eval.yml` 의 제외 대신. ADR 0050 의 4.
- 회수율 폴더는 수트 지문 두 모드 밖이다 — route 만 밖 · 둘 다 안 대신. ADR 0050 의 5.
- 목적 그레이더는 결정론 정규식 하나다 — 심판 대신. ADR 0050 의 6.
- 대조군 `real-nc-found` 를 두지 않는다. ADR 0050 의 7.
- PR 나눔 — B(러너 · 검사 · 지문 · 첫 케이스) · C(남은 다섯) · D(기준선 · 문서). ADR 0050 의 8.

**열어 둔 것**

- R4 ~ R6 의 B2 확인과 예비로 바꿀지 — C 가 그 PR 을 열기 전에 정해 설계 끝의 날짜 항목에 남긴다.
- 케이스마다 픽스처의 도메인과 `recall-found` 의 흔적 낱말 — R1 은 B, 나머지는 C 가 그 PR 본문에 든다(꼴 하나하나는 구현 PR 의 몫, 「설계 문서의 칸」 ⑤).

## ⑤ 검증 계획

시험을 세우는 조각이다(늘 도는 모양 검사를 넓히고 그 변조본을 더한다). 꼴 하나하나와 변조본의 대응은 B 의 PR 본문이 든다.
