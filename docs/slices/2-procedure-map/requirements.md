# 조각 2 — 절차 지도 (2026-10-06 착공)

요구사항이다 — **무엇을 · 왜.** 어떻게 · 경계는 같은 폴더의 `design.md`, 대안이 있던 결정은 ADR 0005 ~ 0009.

## 문제

kickoff 로 시작한 프로젝트에서 **리뷰 회차가 끝나지 않는다.** 처음엔 「PR 이 크다」로 보였는데 크기가 아니었다.

| PR | 파일 | 리뷰 회차 | 리뷰 댓글 | 무엇이 끌었나 |
|---|---|---|---|---|
| 강호쟁패 #1 | 90 | 12 | 76 | 40건이 `Tools/check.mjs` 하나 — 결국 PR 에서 뗐다 |
| 강호쟁패 #3 | 15 | 18 | 168 | 검사기의 입력 모양(`.env` 따옴표 · TOML · IPv6 …)을 한 칸씩 |
| ERP #84 | 14 | 10 | 70 | 호환 판정 검사기 — `40 → 70 → … → 40`, 0 에 닿지 않고 소유자가 닫음 |

설계는 셋 다 먼저 있었다(강호쟁패 ADR-0005 · ERP ADR 0018). 빠진 것은 셋이다.

- 설계에 **보장하는 것 / 보장하지 않는 것 · 받는 입력** 칸이 없었다 — 리뷰가 한 칸씩 채웠다.
- 지적을 **설계에 비춰 가르는 자리**가 없었다 — 강호쟁패 #3 은 Codex 지적 84건 중 81건을 고쳤다.
- **프로젝트 전체의 조각 나눔**이 한쪽에만 있다 — ERP 는 설계도(저장소 밖)에서 단계를 꺼내고, 강호쟁패는 나눔이
  없어 #1 에 착공 문서 · 가설공사 · 검사 스크립트가 붙었다.

통상 IT 구축(SI)은 이것을 범위의 문서 고정과 **변경 관리**로 막는다. 바이브코딩에는 그 절차가 없다.

## 핵심 사용자와 시나리오

- 사용자: 저자 한 명.
- 시나리오: 마스터플랜의 조각 나눔에서 조각을 꺼낸다 → 조각 폴더에 요구사항과 설계를 써 **한 PR** 로 낸다 → 머지되면
  설계 ⑥ 의 나눔대로 구현 PR 을 낸다 — 열어 둔 결정은 그 PR 을 열기 전에 정한다 → 리뷰 지적은 설계 ② · ③ 에
  비춰 가른다 → 조각을 닫으며 마스터플랜의 나눔을 갱신한다. 조각이 마스터플랜의 범위를 벗어나면 마스터플랜을 먼저 고친다.

## 성공 기준

- 절차 지도(`docs/procedure.md`)가 두 층(마스터플랜 → 조각)과 일곱 단계를 정의하고, 맡는 도구가 없는 자리는
  증거와 함께 빈자리로 적혀 있다.
- 강호쟁패 #1 · #3, ERP #84, 그리고 ERP 의 설계도 → 단계 → 조각을 지도에 대면 각각이 어느 단계에서 무엇을
  건너뛰었는지 · 어디에 대응하는지 지도가 가리킨다.
- 의도 · 마스터플랜 · 요구사항 · 설계 틀이 있고, 그 모양이 절차 지도에 고정돼 있다.
- claude-kit 자신이 이 모양으로 선다 — `INTENT.md` · 마스터플랜 · 조각 폴더.
- 이 조각의 PR 리뷰가 3라운드 안에 닫히거나, 넘기면 소유자가 판정한다.

회차가 줄었는지는 이 조각의 기준이 아니다 — 조각 나눔 「리뷰 루프」의 기준이다.

## 하지 않을 일

1. **절차를 실행하는 코드 · 플러그인 · 스킬 · 검사를 만들지 않는다.** 문서만.
2. **변경 관리(리뷰 루프)는 구현하지 않는다.**
3. **계정 스킬(`project-kickoff` · `build-gate`)을 고치지 않는다.** 고칠 자리는 「계정 스킬의 일」로 적는다.
4. **강호쟁패 · ERP 레포를 바꾸지 않는다.** 사례로만 인용한다. ERP 는 다음 단계를 착공할 때부터 따른다(ADR 0008).
5. **SI 에서 버리기로 한 것은 단계로 두지 않는다** — 제안 · 평가 · 계약 · 대금 · 서명 회의 · 두꺼운 산출물.
6. **증거 없는 빈자리에 규칙을 지어내지 않는다.** 요구사항 추적 · WBS · 일정 · 안정화 · 종료 등은 이름만 둔다.
7. **틀에 도메인 칸(게임 · ERP)을 넣지 않는다.**

## 제약

- 마크다운 문서만. `gates.sh` 는 그대로 통과해야 한다.
- 모델 비용 **$0**, 기간 **하루**.
- 리뷰: PR 본문에 설계 ② 를 적고, 그 밖의 지적은 고치지 않고 답글로 넘긴다. 3라운드를 넘기면 소유자가 판정한다.
- 틀은 claude-kit 에만 둔다 — 레포로 가는 길은 조각 나눔 「틀 배포」.

## 로드맵의 근거

순서와 상태는 `docs/master-plan.md` 조각 나눔이 든다. 여기는 그 순서를 매긴 근거다. 순서는 저자가 정했다
(2026-10-06) — 「문서 대조 검사」 · 「README · CLAUDE.md 를 제 역할로 줄이기」를 앞에, 그다음 「틀 배포」 → 「리뷰 루프」
→ 「설계 → 구현 관문」. 리뷰 루프는 그 레포의 설계 ② · ③ 에 비춰 가르는데, 강호쟁패에는 틀이 가기 전까지 설계
문서가 없다 — 그래서 증거가 가장 많은 리뷰 루프보다 틀 배포가 먼저다.

| 조각 | 증거 |
|---|---|
| 문서 대조 검사 | 이 조각에서 드러남 — 살아 있는 문서의 경로 · 절 제목 · 나눔 상태 · 시간에 기댄 문장을 체크리스트만 지킨다(강호쟁패 ADR-0005: 사람이 기억하는 검사는 건너뛴다). 「리뷰 루프」가 설계의 칸을 읽으려면 모양이 먼저 지켜져야 한다 |
| 리뷰 루프 | PR 일곱(ERP #18 · #20 · #71 · #84 · #86, 강호쟁패 #1 · #3) · ERP `docs/리뷰-루프.md` 실물 |
| 틀 배포 | 하지 않을 일 1 이 남긴 것 |
| 설계 → 구현 관문 | PR 하나(강호쟁패 #1 — 착공 문서와 가설공사가 한 PR) |
| 진척 관리 · 단계별 기준선 · 요구사항 추적 · WBS · 일정 · 안정화 · 종료 | 증거 없음. 진척 관리는 GitHub Spec Kit · Kiro 가 조각마다 `tasks.md` 를 둔다는 참고만 있다 — 우리 레포에서 아픈 증거가 생기면 매긴다(저자 결정 2026-10-06) |
