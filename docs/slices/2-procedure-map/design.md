설계다 — **어떻게 · 경계.** 무엇을 · 왜는 같은 폴더의 `plan.md`. 칸의 모양은 `docs/procedure.md` 「설계 문서의 칸」.

## ② 보장하는 것 / 보장하지 않는 것

**보장하는 것**

- 지도가 두 층이다 — 조각은 마스터플랜의 나눔에서 나오고, 닫으며 나눔을 갱신하고, 범위를 벗어나면 마스터플랜을
  먼저 고친다.
- 마스터플랜이 다른 문서가 든 값을 옮겨 적지 않는다 — 주인 없는 목표 · 범위만 직접 든다. README 를 가리키는 것은
  입구(설치 · 배포 경로)뿐이다.
- 기획은 무엇을 · 왜만, 설계는 어떻게 · 경계만 든다.
- 설계 ④ 가 정한 것과 열어 둔 것을 가른다 — 열어 둔 것은 ⑥ 의 어느 PR 이 정하나까지.
- 이 조각이 쓰는 살아 있는 문서에 시간에 기댄 문장이 없다 — 「언제」는 조각 나눔의 줄을 이름으로 가리킨다.
- 지도의 일곱 단계마다 네 칸이 차 있고, 비면 빈자리로 증거(PR) 또는 「증거 없음」과 함께 적혀 있다.
- 강호쟁패 #1 · #3, ERP #84, ERP 의 설계도 → 단계 → 조각이 지도의 어디에 대응하는지 적혀 있다.
- 틀의 제목이 `docs/procedure.md` 와 같고, 틀에 게임 · ERP 전용 칸이 없다.

**보장하지 않는 것(알려진 한계)**

- **강제하지 않는다** — 「문서 대조 검사」 · 「리뷰 루프」 · 「설계 → 구현 관문」.
- **각 레포에 가지 않는다** — 「틀 배포」. 강호쟁패 · ERP 는 바꾸지 않는다. ERP 는 다음 단계를 착공할 때부터
  따른다(ADR 0008). 설계도를 저장소로 들일지는 ERP 가 정한다.
- **회차가 줄어든다는 것** — 「리뷰 루프」의 기준이다.
- 증거 없는 빈자리(진척 · 기준선 · 추적 · WBS · 일정 · 안정화 · 종료)의 절차. 이름만 있다.
- 시스템 구조 문서의 틀. 파일로 둔 증거가 강호쟁패 하나뿐이다 — 지도는 「마스터플랜이 가리키는 살아 있는 문서」로만 적는다.
- kickoff 와의 정합. kickoff 는 `PRD.md` 를 쓰고 조각 나눔 칸이 없다 — 계정 스킬의 일.
- SI 용어와의 일대일 대응. SI 를 근거로 삼되 바이브코딩에 맞게 접었다(기획 하지 않을 일 5).

## ④ 결정

**정한 것**

- 절차 지도를 먼저 그리고, 변경 관리 구현은 그다음 — ADR 0005.
- 기획 + 설계는 한 PR, 구현은 설계 ⑥ 대로 — ADR 0006.
- 마스터플랜은 색인 + 조각 나눔이고 주인 없는 목표 · 범위를 직접 들며, 저장소 안에 산다 — ADR 0007.
- 조각 폴더 · 이름(마스터플랜 · `plan.md` · `design.md`) · 모양은 절차 지도에 · ERP 는 다음 단계부터 · 설계 ④ 의
  열어 둔 결정 — ADR 0008.

**열어 둔 것**

- 지도 본문의 단계별 네 칸과 빈자리의 문구 — PR B 가 사례를 대 보며 정한다.

## ⑤ 검증 계획

- **역검증(손으로):** 강호쟁패 #1 · #3, ERP #84 를 지도에 대 본다. 지도가 「어느 단계에서 무엇을 건너뛰었나」를
  가리키지 못하면 지도를 고친다. ERP(설계도 → 단계 → 조각)와 강호쟁패(범위는 있고 나눔이 없다)가 두 층에 어떻게
  대응하는지도 설명돼야 한다. 결과는 `docs/procedure.md` 의 사례 절에 남긴다.
- **틀 자기 적용:** 이 조각의 `plan.md` · `design.md` 가 `docs/procedure.md` 의 필수 제목을 갖는다. 틀은 그 제목을
  그대로 옮긴다.
- `./scripts/gates.sh` 통과 — 스크립트를 건드리지 않았으니 그대로여야 한다.
- 모델을 부르지 않는다.
