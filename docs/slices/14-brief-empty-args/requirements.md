# 조각 14 — 브리핑 커맨드의 빈 인자 (2026-10-13 착공)

요구사항이다 — **무엇을 · 왜.** 어떻게 · 경계는 같은 폴더의 `design.md`, 대안이 있던 결정은 ADR 0023.

## 문제

**`/audit-brief` 를 인자 없이, 또는 기준만으로 부르면 커맨드 본문의 `$0` · `$1` 이 글자 그대로 남는다.** 커맨드는 「`$0` 가 비어 있으면
먼저 물어보세요」 · 「`$1` 가 주어졌으면 그 감사자를, 아니면 … 물어보세요」로 빈 인자를 다루는데, 짝이 없는 번호 자리표시는 비지 않는다.
Claude Code 문서(code.claude.com/docs/en/skills, 2026-10-13)가 적는다 — 「짝이 없는 번호 자리표시(`$2` 등)는 바뀌지 않고 남는다.
프런트매터 `arguments` 의 이름 자리표시는 짝이 없으면 빈 문자열이 된다.」

- 강호쟁패 #11 의 Codex 리뷰가 사본 `audit-brief.md` 에서 짚었다. 사본은 원본의 바이트라 **원본의 결함**이고, 다른 레포에서도 같은 말이다
  (조각 13 「닫으며」 넘긴 것).
- 지금 막는 것은 하나다 — 「하나」 단계가 기준의 글자에서 `$` 를 걸러 멈추므로, 인자 없이 부르면 틀린 기준으로 diff 를 뽑지는 않는다. 그러나
  멈추는 까닭이 「기준이 없다」가 아니라 「기준에 못 쓰는 글자가 있다」라, 커맨드가 약속한 「기본 브랜치인지 · 머지 베이스인지 · 배포
  태그인지」를 묻는 길로 가지 않는다.
- **기준만 주면 막는 것이 없다.** `/audit-brief origin/main` 은 브리핑을 다 쓴 뒤 「넷」 단계에서 `$1` 을 글자 그대로 본다 — 감사자가
  「주어졌다」고 읽거나 `@vibe-audit:$1` 을 그대로 부를 수 있다. 커맨드의 `argument-hint` 가 감사자를 선택으로 적어(`[감사자 이름]`)
  기준만 주는 부름은 정상 사용이다.
- 이 결함을 재는 케이스가 없다. 수트의 케이스 스물다섯은 다 감사자를 재고, 커맨드는 `brief-used` · `brief-absent` 도 부르지 않는다
  (그 두 `case.yaml` — 「커맨드는 이 케이스에서 부르지 않는다」).

## 핵심 사용자와 시나리오

- 사용자: 저자 한 명, 그리고 claude-kit · 사본 레포 · 플러그인을 깐 레포에서 `/audit-brief` 를 부르는 세션.
- 시나리오: 저자가 대화형 세션에서 PR 을 감사하려고 `/vibe-audit:audit-brief origin/main` 만 친다 → 세션이 기준을 SHA 로 굳히고 브리핑을
  써 검사기를 PASS 로 지난다 → 감사자가 비어 있으니 감사자를 짐작해 부르지 않고 어느 감사자를 부를지 묻는다 → 저자가 답하면 그 감사자를
  브리핑 경로와 함께 부른다. 저자가 인자 없이 `/vibe-audit:audit-brief` 만 치면 세션은 git 을 돌리기 전에 기준이 기본 브랜치인지 · 머지
  베이스인지 · 배포 태그인지 묻는다.

## 성공 기준

1. 커맨드에 번호 자리표시가 없다 — `vibe-audit/commands/audit-brief.md` 가 기준 · 감사자를 프런트매터 `arguments` 의 이름 자리표시로 받고,
   본문에 `$0` · `$1` · `$ARGUMENTS` 가 없다. `claude plugin validate ./vibe-audit` 가 통과한다.
2. 기준만 준 부름을 재는 케이스가 있다 — 새 케이스(설계 ② K1)가 바뀐 커맨드로 세 회차 다 덫(감사자를 짐작해 부름)을 밟지 않고 대조군
   (브리핑을 씀)을 지나며, 케이스 점수가 전수 문턱 0.8 이상이다. 옛 커맨드의 점수도 같은 케이스로 재어 적는다 — 옛 커맨드가 덫을 한
   번도 밟지 않으면 그 사실을 적는다(설계 ② 보장하지 않는 것).
3. 수트 검사가 그 케이스의 모양을 문다 — `verify-evals.py` 가 커맨드 케이스의 모양(설계 ② V1 ~ V3)을 보고, 그 갈래를 끈 변조본이
   `bite-gates.sh` 에서 떨어진다.
4. 글자 예산 — 커맨드의 호출 시 글자가 천장 4,500 안이고 천장은 그대로다. `budget.txt` 의 diff 가 늘거나 준 글자를 밝힌다.
5. 플러그인 판 — `vibe-audit` 의 `plugin.json` 판이 오른다(`CHECKLIST.md` 「플러그인의 파일을 고쳤다면」).
6. 인자 없이 묻는다 — 단계 5 에서 저자가 판이 오른 플러그인을 받은 대화형 세션에서 `/vibe-audit:audit-brief` 를 인자 없이 불러, 세션이 git
   을 돌리기 전에 기준을 묻는 것을 본다.
7. `./scripts/gates.sh` 가 로컬과 CI gate 잡에서 통과한다 — 검사의 수는 그대로다. 구현 PR 의 route 수트가 CI 에서 통과한다.

## 하지 않을 일

1. **사본을 다시 심지 않는다** — ERP · 강호쟁패의 사본 커맨드는 옛 글자 그대로 남고, 다음 심기에서 새 커맨드를 받는다(ADR 0023 의 4).
   커맨드는 공통 절이 없어 `verify-copies.py` 가 내용을 견주지 않으므로 대장은 갈리지 않는다.
2. **후보 대장에 줄을 두지 않는다** — 사본의 차이에서 온 후보가 아니라 리뷰가 짚은 원본의 결함이다. `feedback.json` 의 후보는 사본 덩어리의
   내용 해시가 키다(`docs/schema.md`). 조각 5 PR C 의 `audit-internal` 고침과 같은 꼴이다(`docs/eval-log/2026-10.md` 2026-10-07).
3. **글자 예산의 천장을 올리지 않는다** — 넘으면 커맨드 안에서 압축한다(ADR 0004). 그래도 넘으면 이 조각에서 정하지 않고 저자에게 올린다.
4. **커맨드의 일을 바꾸지 않는다** — 모으는 명령 · 브리핑의 모양 · 검사기 · 남기는 것은 그대로다. 빈 인자를 받는 자리와 그것을 가리키는
   문장만 고친다. 커맨드를 스킬(`skills/audit-brief/SKILL.md`)로 옮기지 않는다(ADR 0023 의 1).
5. **번호 자리표시를 키 없이 무는 검사를 세우지 않는다** — 회귀는 새 케이스가 잰다. 같은 결함이 다른 커맨드 · 스킬에서 나오면 조각 나눔에
   줄을 더한다.
6. **인자 없는 부름을 수트 케이스로 재지 않는다** — 되먹임 한 건에 케이스 하나다(`CLAUDE.md` 「작업 방식」). 인자 없는 쪽은 아무것도 안 하는
   세션도 통과해 대조군이 서지 않는다(ADR 0023 의 2). 성공 기준 6 의 단계 5 로 본다.
7. **러너와 정규식 그레이더의 고정한 규칙을 바꾸지 않는다**(`AGENTS.md` 「Review guidelines」) — 새 케이스는 지금의 러너 · 그레이더 종류로
   잰다.

## 제약

- 스택: bash · python3 표준 라이브러리 · git · Claude Code CLI(`claude plugin validate` · `run-evals.sh`).
- 모델 비용: 구현 PR 의 route 수트 — 커맨드 · `verify-evals.py` 가 수트 지문(`eval-key.py route --list`)에 들어 PR 머리마다 돈다(한 번
  30회). 새 케이스는 판정 케이스처럼 전수(`workflow_dispatch`)나 `run-evals.sh --case` 로 잰다 — 옛 커맨드 한 번 · 새 커맨드 한 번.
- 글자 예산: `audit-brief` 호출 시 4,458 / 천장 4,500(2026-10-13 `main` 83ac86d) — 여유 42자. 상시는 285 / 900, 합계 5,223 / 5,600.
- 기간: **이틀**.
- `./scripts/gates.sh` 는 지금의 수 그대로다 — `verify-evals.py` 와 `bite-gates.sh` 는 이미 그 안에 있다.
- 리뷰: PR 본문에 설계 ② 를 적고, 착공 PR 도 구현 PR 도 스킬 `slice-review` 로 가른다. **3라운드**를 넘기면 소유자가 판정한다.
