# vibe-audit

목적별로 범위를 좁힌 **읽기전용 감사자 2종**.

공장은 품질부서를 생산부서에서 떼어 놓고, 감사를 목적별로 쪼갭니다. ISO 심사원은 화학사고 위험을 보지 않고, PSM 점검원은 고객 도면 관리를 보지 않습니다. 시야가 좁게 설계되어 있어서 깊게 봅니다.

이 플러그인은 그 두 가지를 코드 감사에 옮긴 것입니다.

## 왜 에이전트인가

각 감사자의 프론트매터에는 이렇게 적혀 있습니다.

```yaml
tools: ["Read", "Grep", "Glob"]
```

`Edit` · `Write` · `Bash` 가 **없습니다.** 고치라고 시켜도 못 고칩니다.

"감사자는 고치지 않는다"를 문서에 쓰는 것과, 애초에 설비 열쇠를 주지 않는 것의 차이입니다. 스킬로는 지시밖에 못 하고 지시는 세션 분위기에 따라 흔들립니다 — 부적합을 찾고 나서 "이건 한 줄이니 바로 고칠게요"가 나오는 구조입니다. 도구 제한은 지시가 아니라 구조입니다.

감사자가 고친 코드는 **아무도 검사하지 않은 코드**가 됩니다.

## 감사자 2종

| 이름 | 무엇만 보는가 | 현장 대응 |
|---|---|---|
| `audit-data` | 스키마 · 마이그레이션 · 트랜잭션 · 되돌림 | 설비 변경 관리(MOC) |
| `audit-internal` | 문서에 적은 규칙 대비 실제 코드 | 자체 감사(1자) |

둘이 보는 범위는 겹치지 않습니다. 각 감사자의 「보지 않는 것」 절에 담당이 명시되어 있어, 범위 밖을 발견하면 적지 않고 담당만 넘깁니다. 시크릿 · 권한, 테스트 · CI, 공개 API 계약, 관측 · 롤백을 보던 감사자 넷은 은퇴했습니다(2026-11, 조각 「감사자 넷 은퇴」) — 은퇴 전 모양은 태그 `v-archive-2026-11` 에 있습니다.

## 은퇴한 감사자의 자리

시크릿 · 권한(`audit-secrets`), 테스트 · CI · 평가셋(`audit-quality`), 공개 API 계약(`audit-contract`), 관측 · 롤백(`audit-ops`)은 2026-11 에
은퇴했습니다. 레포 맥락을 한 줄 둔 일반 리뷰 도구가 놓친 결함 묶음에서 이 감사자들보다 뒤지지 않았기 때문입니다(claude-kit
`docs/eval-log/2026-11.md` 「맥락 한 줄 팔」 · ADR 0090 · 0091). 남는 감사자는 그 자리를 「보지 않는 것」으로 넘깁니다. 아래는 넘길 곳의
안내일 뿐이고, 이 플러그인이 그 도구를 부르거나 재지 않습니다.

| 자리 | 넘길 곳 |
|---|---|
| 시크릿 · 자격증명 · 권한 경계 | Claude Code 의 `/security-review` |
| 테스트 · CI 게이트 · 공개 API 계약 · 하위 호환 | 리뷰 도구(`pr-review-toolkit` · `code-review` 같은) — 그 레포의 `CLAUDE.md` 에 「하지 않을 일」 · 로컬 전용 값을 결함으로 올리지 말라는 줄을 두면 오검이 준다 |
| 관측 · 롤백 · 배포 직전 | 아래 배포 전 체크리스트 — 사람이 본다 |

### 배포 전 체크리스트

은퇴한 `audit-ops` 의 체크 항목에서 배포를 막을 만한 것만 골랐습니다. 감사자처럼 근거를 모아 주지 않으니, 항목마다 「어디서 확인했나」를 적어 두세요.

- [ ] **에러가 삼켜지는 곳이 없다** — 빈 `catch`, 로그만 찍고 성공으로 돌려주는 분기, 무시되는 프로미스
- [ ] **에러 추적 도구가 프로덕션에서 켜져 있다**
- [ ] **요청 하나를 끝까지 따라갈 식별자가 있다** — 요청 ID · 상관관계 ID
- [ ] **로그에 판단에 필요한 값은 있고, 자격증명 · 개인정보는 없다**
- [ ] **조용히 쌓이는 실패가 없다** — 백그라운드 작업 · 큐 · 크론 · 웹훅 재시도
- [ ] **무엇이 잘못되면 사람에게 알림이 간다** — 대시보드만 있고 알림이 없으면 아무도 안 본다
- [ ] **롤백 절차가 문서로 있고, 한 번이라도 해 봤다** — 코드만 되돌리면 되는지, 데이터(마이그레이션)까지 얽히는지
- [ ] **백업이 있고 복구를 해 봤다**
- [ ] **헬스체크가 프로브 용도에 맞다** — 레디니스는 의존성을 보고, 라이브니스는 보지 않는다
- [ ] **모델을 부르는 기능이면** — 재현되는 트레이스, 토큰 · 비용 상한, 도구의 승인 · 범위 제한, 요청 로그의 모델 · 프롬프트 판

## 설치

로컬 대화형 세션은 마켓플레이스에서:

```bash
claude plugin marketplace add pdw96/claude-kit
claude plugin install vibe-audit@pdw96-kit
```

앱에서 연 클라우드 세션은 claude.ai 계정에 이 마켓플레이스를 붙여 두면 계정 동기화로 받는다. 특화가 있는 레포와 동기화가 닿지 않는 세션은 그 레포의 `.claude/agents/` 에 사본을 둔다 — `scripts/sync-agents.sh` 와 저장소 뿌리 README 「설치」 참고. 사본 레포의 앱 세션에는 두 벌이 뜨고, 스코프 없는 이름(`@audit-data`)이 사본이다.

## 쓰는 법

```
@audit-data 이번 PR 의 마이그레이션
@audit-internal 저장소 전체
```

또는 새 세션으로:

```bash
claude --agent audit-internal
```

**한 번에 하나씩** 돌리세요. 둘을 한꺼번에 돌리면 둘 다 얕아집니다 — 범위를 좁히는 것이 이 플러그인의 전부입니다.

감사 대상 코드를 방금 이 세션에서 작성했다면 **새 세션에서 돌리세요.** 자기가 세운 전제를 그대로 들고 검사하게 됩니다.

## 결과를 어떻게 다루나

각 감사자는 번호 매긴 부적합 목록(`NC-1`, `NC-2` …)과 **「안 본 것」**을 냅니다. 안 본 것이 결과의 일부입니다 — 이게 없으면 "감사했으니 괜찮다"는 잘못된 안심이 생깁니다.

부적합은 파일이나 이슈로 남기세요. 등록되지 않은 "나중에 고쳐야지"는 예외 없이 사라집니다.

그리고 공장에서 부적합을 닫는 권한은 "고쳤다"가 아니라 **유효성 검증**에 있습니다. 고친 뒤 **같은 감사자를 다시 돌려** 재발하지 않았는지 확인할 때 닫습니다. 포스트모템 액션 아이템이 무력해지는 지점이 정확히 여기입니다.

그래서 **기록을 `.claude/audits/<감사자 이름>-<날짜>-<시각>.md` 로 남기세요** — 시각은 초까지 붙이고, 같은 이름이 이미 있으면 덮지 말고 끝에 `-2` 를 붙입니다. 고친 뒤 같은 날 다시 돌린 기록이 앞의 것을 덮으면 다음 회차가 이을 번호가 사라집니다. 레포가 대장을 따로 두었으면(`CLAUDE.md` 등이 가리키는 곳) 그 대장에 등록하고, 감사자도 그 대장을 지난 기록으로 읽습니다. **한 작업트리에서는 감사를 하나씩 돌리세요 — 감사자가 달라도** — 브리핑 자리(`.claude/audit-brief.md`)가 하나라 서로의 것을 덮고, 같은 지난 기록을 읽으면 같은 다음 번호를 뽑아 서로 다른 결함에 붙입니다. 감사자는 쓰는 도구가 없어 스스로 남기지 못합니다. 다음 회차의 같은 감사자가 이 폴더에서 자기 이름이 붙은 가장 최근 기록을 찾아 NC 번호를 잇습니다 — 지난 NC-1 이 그대로 있으면 이번에도 NC-1 이고, 해소된 번호는 은퇴해서 다른 결함에 다시 가지 않습니다.

그리고 지난 NC 가 이번 목록에 없을 때 **「해소」와 「이번엔 안 봄」을 가릅니다.** 해소는 고쳐진 자리를 이번에 직접 본 경우이고, 범위 밖이라 안 본 것은 안 본 것으로 남습니다. 둘을 섞으면 「안 본 것」을 두는 이유가 시간 축에서 그대로 무너집니다 — 안 본 자리가 고쳐진 자리로 기록됩니다.

## 감사 계획과 부적합 대장

이 플러그인은 개별 감사만 합니다. 부적합을 재감사로 닫힐 때까지 따라가는 대장은 `vibe-slice` 플러그인의 틀(스킬 `slice-docs` 의 `templates/`)을 베껴 세웁니다 — 감사자는 그 대장을 `CLAUDE.md` 가 가리키면 지난 기록으로 읽습니다. 언제 돌릴지는 조각 요구사항 「제약」의 감사 회차가 정합니다 — 고르는 법은 claude-kit [절차 지도](https://github.com/pdw96/claude-kit/blob/main/docs/procedure.md)의 「감사 회차」입니다. 아래 표는 그 원천 가운데 하나(바뀐 것 → 감사자)입니다.

대략의 주기:

| 시점 | 돌릴 감사자 |
|---|---|
| 스키마 · 마이그레이션 · 트랜잭션을 건드린 PR | `audit-data` |
| 조각 서너 개 머지한 뒤 | `audit-internal` |

## 이 감사자들은 감사받는가

감사자가 남에게 요구하는 검사 — 평가셋 · 회귀 판정 — 를 이 플러그인이 자기 자신에게 적용한
자리가 `evals/` 입니다.

```bash
./scripts/run-evals.sh
```

케이스 열셋이 재는 것은 아래 표입니다.

| 무엇 | 케이스 | 재는 것 |
|---|---|---|
| 판정 | 열 | **오검율**과 판정의 근거. 실제 되먹임에 붙은 하나(담당인 것 넘기기)와 사본 비교에서 온 둘(운영 표를 잠그는 마이그레이션 · 주석에만 적힌 결정)에, 브리핑이 있을 때와 없을 때 · 감사한 커밋을 기록에 적는가 셋 · 회차 잇기(첫 회차 · 이어지는 회차) 둘 · 조각 폴더의 범위(닫힌 조각 · 옛 `PRD.md`) 하나 · 심각도의 기준(높음과 낮음) 하나 |
| 트리거 | 셋 | 부른 감사자가 뜨는가, `audit-data` 가 청하지 않아도 제 자리에서 뜨는가, 무관한 요청에 아무도 안 뜨는가 |

거짓 지적을 두어 번 내면 아무도 감사자를 안 부르므로, 이 도구에서 가장 비싼
결함이 오검입니다. 판정 케이스의 픽스처에는 **진짜 부적합이 하나씩** 들어
있습니다. 아무것도 안 내는 감사자가 만점을 받는 것을 막는 대조군입니다.

`./scripts/run-evals.sh` 는 인자 없이 열셋을 다 돌립니다. PR 의 CI 는 트리거
셋만 문턱 1.0 으로, 전수는 `workflow_dispatch` 로 문턱 0.8 에서 돌립니다.

자세한 것은 `evals/README.md` 「케이스」 · 「재는 법」.

## 한계

- 감사자는 **읽기만** 하므로 테스트를 돌려보지 못합니다. 실행이 필요한 검증은 CI 쪽 일입니다.
- **`audit-data` 는 요청하지 않아도 뜹니다.** 스키마 · 마이그레이션을 바꿨다는 말이 나오면 묻는 것이 다른 일이어도 답하기 전에 돌아갑니다. 그만큼 **모델 사용량과 지연이 늡니다.** 원치 않으면 그 감사자의 `description` 에서 해당 문장을 지우세요(사본은 그 레포 것이니 고쳐도 됩니다). 재는 법은 `evals/README.md` 「트리거 정확도」.
- `audit-internal` 은 부르지 않으면 뜨지 않습니다 — 바쁠 때 안 부르게 되는 구조라, 중요한 검사는 결국 CI 게이트로 옮겨야 합니다.
